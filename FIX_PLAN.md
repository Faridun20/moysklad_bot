# FIX_PLAN — план исправлений (аудит 2026-06)

Источник: аудит логики (деньги, жизненный цикл заказов, МС-синк, авторизация API,
время/TZ) + ревью диффа сессии (`216e0dc..7b21cd6`). Каждая находка
**подтверждена** отдельным верификатором. REFUTED-пункты вынесены в конец как
«не баг / hardening».

## Как пользоваться этим планом (для фиксер-агентов)

- Работай **по одному Work Package (WP)** за заход. У каждого: проблема → корень →
  файлы/якоря → что сделать → тесты → критерий приёмки → зависимости.
- **Якоря — имена функций**, а не номера строк (строки сдвигаются). Номера даны
  как ориентир на момент аудита.
- **Гейты перед коммитом (обязательно):** `pytest tests/`, `ruff check .`, `mypy`,
  фронт — `powershell -ExecutionPolicy Bypass -File scripts/test-js.ps1`.
  Денежное ядро менял → прогони весь `pytest`, не точечно.
- **Конвенции (CLAUDE.md), не нарушать:** деньги — целые копейки (`services/money`);
  роль — `services.roles.cached_role`; HTML — `utils.helpers.esc()`; period-порог
  считаем в Python, не в SQL `NOW()`; `_authorize(...)` на каждом `/api/*`; ошибки МС
  в лог — через `redact_ms_error`; `init_db` только CREATE TABLE, ALTER — в
  `run_migrations`.
- **Один WP = один коммит** (формат как в репо, `Co-Authored-By: Claude ...`).
  Денежные/гард-фиксы — обязательно с регресс-тестом в том же коммите.
- Многие денежные фиксы лежат в `services/database.py` — **бери P0 последовательно**,
  чтобы не ловить конфликты; P3/P4 (разные файлы) можно параллелить.

## WP-04. Запрет смешения валют при закрытии заказа (link_payment / close)
**Подтверждено.** `_maybe_close_order_after_payment` (`:4481`) сравнивает
`SUM(payment cents)` всех валют против `total cents` заказа **без `convert_to_base` и
без фильтра по валюте**. `link_payment_to_order` (`:4304`, эндпоинт
`/api/payments/link` boss-only `:1353`) линкует standalone-платёж любой валюты к
заказу **без проверки валюты**. Standalone-платежи легитимно бывают в любой
`ALLOWED_CURRENCIES`.
**Последствие:** платёж 5 000 000 UZS, прилинкованный к заказу $5000 →
`500000000 ≥ 500000` → заказ закрыт как оплаченный, долг $4600 испаряется.
**Сделать (выбрать согласованно с WP-05/06):**
- В `_maybe_close_order_after_payment` суммировать платежи **в базовой валюте**:
  либо `WHERE currency = <order.currency>` + сравнивать в валюте заказа, либо
  конвертировать каждую сумму через `convert_to_base` и сравнивать базовый total.
  Рекомендуется: считать всё в базовой валюте (как `get_agent_current_debt:1208`).
- В `link_payment_to_order` (или в эндпоинте) — отклонять линковку при
  несовпадении валют, ИЛИ конвертировать корректно. Минимум: явный отказ
  `payment.currency != order.currency` пока нет конверсии при закрытии.
**Тесты:** UZS-платёж к USD-заказу не закрывает заказ ложно; same-currency
закрывает корректно; смешанные подтверждённые платежи суммируются в базе.
**Критерий:** заказ закрывается только когда полученное ≥ долга в общей валюте.

## WP-05. Сдачи (cash_deposits): валюта и взаимоучёт с платежами
**Подтверждено (две связки).**
(A) `confirm_cash_deposit` (`:2228`) закрывает заказ только если
`confirmed_deposit_cents >= net_owed`, **игнорируя confirmed-платежи**;
`_maybe_close_order_after_payment` игнорирует confirmed-сдачи;
`get_agent_current_debt` (`:1179`) **не вычитает** аллокации сдач →
заказ, оплаченный наполовину платежом + наполовину сдачей, не закрывается никогда,
а долг частично-покрытого заказа завышен.
(B) `cash_deposits` **не имеет колонки валюты** (хранится в базовой), но FIFO
`create_cash_deposit` (`:2163`) и `get_manager_open_orders_for_deposit` (`:1783`)
сравнивают базовые cents сдачи против cents в валюте заказа **без `convert_to_base`**
→ $400-сдача против 5 000 000 UZS аллоцирует только 400.
**Сделать:**
- Ввести единую функцию «покрытие заказа» = confirmed-платежи (в базе) +
  confirmed-сдачи (в базе) − возвраты; использовать её и в `confirm_cash_deposit`,
  и в `_maybe_close_order_after_payment`, и в `get_agent_current_debt` (вычитать
  аллокации сдач). Это устраняет (A) системно.
- В FIFO-аллокации и `get_manager_open_orders_for_deposit` приводить `remaining`
  заказа к базовой валюте через `convert_to_base` перед сравнением со сдачей (база).
  Заказы с валютой без курса — исключать/помечать, не аллоцировать криво.
**Зависимость:** согласовать «базовую валюту покрытия» с WP-04 (одна формула).
**Тесты:** half-payment+half-deposit → заказ закрыт, долг 0; UZS-заказ + $-сдача
аллоцируется по курсу; долг частично-покрытого заказа учитывает сдачу.
**Критерий:** долг/закрытие согласованы между платежами и сдачами, кросс-валюта
считается через курс.

## WP-09. mark_paid без гарда статуса + delete_order оставляет orphan-платежи
**Подтверждено (реалистичный путь через `reject_order_to_draft`).**
`mark_order_paid` (`:5121`) и `/api/orders/mark_paid` (`:3258`) проверяют только
`payment_type=='credit'` и `paid_confirmed_at`, **не статус**. `delete_order` (`:4245`,

выкл.). `confirm_payment` не проверяет существование заказа.
**Путь:** boss отклоняет кредит-заказ в draft (`reject_order_to_draft` не сбрасывает

заказе) → `delete_draft` → платёж осиротел → `confirm_payment` подтверждает его →
деньги в кассе/МС против несуществующего заказа.
**Сделать:**
- `mark_order_paid`: добавить гард статуса (разрешать только на активных
  одобренных/отгруженных кредит-заказах; запретить draft/pending/rejected/cancelled).
- `delete_order`: блокировать удаление, если по заказу есть ЛЮБЫЕ payments
  (`WHERE EXISTS payments`), ИЛИ каскадно удалять их в той же транзакции.
  Предпочтительно — блокировать с понятной ошибкой.
**Тесты:** mark_paid на draft/pending → отказ; delete draft с платежами → отказ
(или каскад без orphan'ов); confirm_payment на удалённый заказ невозможен/без эффекта.
**Критерий:** не возникает confirmed-платежа без существующего заказа.

## Часть B — Telegram

**TG-1 проверен: нас не задевает.** Ограничение Bot API 10.2 на вызов методов
Mini App с чужого домена включилось 20.07.2026 автоматически. WebApp отдаётся с
нашего же origin (`/` и `/static` одним FastAPI-приложением), API зовётся
относительными путями, в iframe себя не встраивает; `telegram-web-app.js`
грузится с telegram.org — это сам SDK, а не вызов методов с чужого домена.

**TG-2..TG-7 заблокированы версией библиотеки.** В проекте `aiogram==3.7.0`
(Bot API 7.4). Ни одной из нужных фич в ней нет — проверено интроспекцией:

| Задача | Требует | Есть в aiogram 3.7.0 |
|---|---|---|
| TG-3 `date_time`-entity | Bot API 9.5 | нет |
| TG-4 `style` у кнопок | Bot API 9.4 | нет |
| TG-5 `CopyTextButton` | Bot API 7.11 | нет |
| TG-2 ephemeral-сообщения | Bot API 10.2 | нет |
| TG-6 `sendRichMessage` | Bot API 10.1 | нет |
| TG-7 топики в личке | Bot API 9.3 | нет |

Значит первым шагом идёт **обновление aiogram** — отдельной задачей с
регресс-прогоном всех хендлеров: между минорными 3.x были ломающие изменения
(фильтры, `Bot(parse_mode=…)`, сигнатуры middleware). Делать это вместе с
фичами нельзя — иначе непонятно, что сломалось: апгрейд или новая разметка.

## Что это меняет в бюджете

- реконсиляция: 1500 запросов в час → 15;
- остатки: полный срез каждые 2 с → дельта (не входит в подорожавшие) + один
  полный pull в сутки;
- параллельность: 8+8 одновременных → 4 на процесс, в рамках лимита;
- 429 больше не лечится вслепую: 1073 не уходит в длинный backoff, а доля 429
  в окне открывает брейкер до того, как аккаунт словит автоотключение.

Остались `run_ms_sync_retry` (до 200 запросов каждые 15 минут — MS-3) и N+1 в
аналитике (MS-6). Обе задачи снижают трафик, но не блокируют сентябрьскую
ступень — после MS-2/4/5 бюджет держится.
