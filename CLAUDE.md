## Architecture

Детали в `ARCHITECTURE.md`. Главное: `BOT_MODE` env переключает процесс между `all` / `bot` / `webapp`. На Railway prod два сервиса (`moysklad_bot` + `Webapp`) с разными `BOT_MODE`, общий Postgres + Redis через Project Shared Variables.

**Разделение бот ↔ WebApp (T3.3).** Бот = уведомления + решения по ним + то,
чего в WebApp нет. Работа (заказы, каталог, финансы, аналитика, сдачи,
возвраты, лимиты, курсы, цены) — только в WebApp; дублирующие экраны из бота
вырезаны вместе с `handlers/{analytics,stock,credit,pricing,debts}.py`.
Не добавляй в бота экран, который уже есть в WebApp: снятые команды перечислены
в `handlers.start._RETIRED_COMMANDS` и отвечают подсказкой, где искать
операцию. В боте остаются: кнопки-решения на push-карточках (`req_*`, `pay_*`,
`dep_*`, `ret_*`, `mdr_*` — заявки на сделки по технике, `unfreeze:`), ops/admin-команды без API-аналога (`/audit`,
`/log`, `/users`, `/addrole`, `/deactivate`, `/reactivate`,
`/frozen`, `/printer`),
`/find`, `/ship`, `/cancel`, `/shipments`, `/pay` (в автокомплите руководителя —
только `/start`, `/find`, `/machine_deals`, `/cancel`), а из техники — только
просмотр (`/machines`, карточка, `/machine_deals`) и `/hours <id> <часы>`
(показание снимают с площадки, где открыть WebApp дольше, чем набрать два
числа).
Новую callback-кнопку рисуешь — проверь, что на неё есть хендлер:
`tests/test_bot_trimmed.py::test_no_dangling_callback_buttons_in_bot_code`
сканирует все `callback_data` в `handlers/`, `tasks/`, `utils/`.
Кнопка входа в WebApp — `handlers._ui.webapp_keyboard()` (только https-URL,
иначе Bot API отвергнет сообщение целиком).

## Conventions (нетривиальные)

**DB:**
- `init_db()` делает ТОЛЬКО `CREATE TABLE IF NOT EXISTS`. **Инкрементальных
  миграций в РАБОЧЕМ коде нет**: `ALTER TABLE` запрещён везде, кроме
  `scripts/` (`tests/test_schema_single_pass.py::test_no_alter_table_anywhere_in_project`),
  `run_migrations()` в `services/database.py` не существует и его отсутствие
  тоже под тестом. Нужна новая колонка в таблице, которая уже на проде, —
  два законных пути:
  - **отдельная таблица-sidecar** (прецеденты: `container_supply`,
    `container_item_links`, `machine_deal_payments`) — по-прежнему первый
    выбор, если колонка логически отделима;
  - **колонка в `_create_tables` + разовый `python -m scripts.apply_legacy_columns
    --apply`** — когда поле принадлежит самой сущности и sidecar ради имени
    хуже (так приехали `orders.fx_rate_to_base` / `payments.fx_rate_to_base`).
    Свежая база берёт колонку из определения таблицы, существующую догоняет
    скрипт; он РУЧНОЙ и со старта не вызывается — стережёт
    `test_alter_script_is_not_wired_into_startup`. Хвост до T1.1 у него под
    отдельным `--legacy`: там колонки-призраки, вычищенные в T1.2.
  Data-миграции и сидинг настроек — в `run_backfills()`, вызывается из
  `tasks/migrate.py` — а он идёт на КАЖДОМ `docker compose up`. Поэтому разовые
  миграции (`ONE_TIME_BACKFILLS`) выполняются один раз на базу — отметка
  `backfill_done:<имя>` в `app_settings`, повтор только явно:
  `python -m tasks.migrate --rerun-backfill <имя>|all`. Каждый старт гоняется
  лишь сидинг, который вставляет отсутствующее. Новую data-миграцию, которая
  МЕНЯЕТ строки (особенно деньги), — только в `ONE_TIME_BACKFILLS` или в `scripts/`.
- **Количества — `qty_type` (NUMERIC на Postgres) во ВСЕХ таблицах**, не REAL:
  REAL там float4, 2.3 хранится как 2.2999999523, и дробный возврат не
  закрывал заказ. Драйверы отдают Decimal — приводи к float на границе чтения
  (`database._item_row`, `containers._qty_floats`, как у `stock`), иначе
  `json.dumps` даёт 500. asyncpg кладёт Python float в NUMERIC двоичным хвостом
  (2.29999999999999982…) — `adb_core._pg_args` переводит float-параметры в
  `Decimal(repr)`, не обходи его прямым `conn.execute`.
- **Индексы — `database._index_ddls()`**, один источник для `_create_indexes` и
  сверки старта. Отказ создания — ERROR в лог, а `startup_checks` сверяет имена
  индексов, типы NUMERIC/BIGINT и ICU-коллацию и шлёт алерт. Убираешь индекс —
  имя в `DROPPED_INDEXES` (на базе его снимет `scripts/apply_constraints`).
  UNIQUE на `(acc_day_closes.account_id, close_date)` нет намеренно: сверка
  кассы дважды за день законна.
- **FK/CHECK денежных и складских таблиц живут только на проде** (ставит
  `scripts/apply_constraints`, в DDL их нет — SQLite не добавит их к
  существующей таблице). Значит: удаляй детей ДО родителя, статусы — только из
  списка в скрипте (граф заказа берётся из `order_workflow.TRANSITIONS`), и
  проверяй новый путь записи `tests/test_db_constraints_postgres.py::
  test_constraints_hold_for_real_service_flows`. Postgres проверяет CHECK у
  вставляемой строки UPSERT'а ДО конфликта — поэтому списание остатка идёт
  UPDATE'ом (`warehouse._apply_stock_delta`), а не `INSERT … ON CONFLICT`.
- **Сортировка и поиск по названию:** `ORDER BY {adb_core.order_by_name('name')}`
  (ICU `ru-RU-x-icu` на Postgres — Alpine/musl иначе сортирует по кодам:
  «Zeta, alfa, Ёлка, Абрикос»), LIKE — `adb_core.name_search_sql/
  name_search_param` (нижний регистр и ё→е с обеих сторон).
- Синхронный пул ставит `idle_in_transaction_session_timeout` (5 мин,
  `PG_IDLE_IN_TX_TIMEOUT_MS`, 0 — снять): `with get_conn()` с сетевым вызовом
  внутри больше не держит снимок и блокировки часами.
- Webapp endpoint'ы: `services.async_db as adb` (`await adb.get_user(uid)`) — обёртка через `asyncio.to_thread`. В bot handlers — то же или явный `asyncio.to_thread`.
- Роль читай через `services.roles.cached_role(user_id)` (TTL 30s, одна запись кэша с флагом деактивации — один SELECT на оба факта) и предикаты `is_boss / can_create_orders / ...`. НЕ через `services.database.get_role` напрямую — обойдёшь кэш. **Деактивация:** `get_role` отдаёт `guest` если `user_roles.deactivated_at` стоит → деактивированный теряет ВСЕ права. `deactivate_user/reactivate_user` (адмін, `/deactivate`/`/reactivate` + webapp `/api/users/deactivate`).
- **Временно: менеджер = + кладовщик + бухгалтер** (решение владельца: отдельных сотрудников пока нет, босс проверяет работу). Совмещение — одна таблица `services.roles.ROLE_ALSO_ACTS_AS` (зеркало `ROLE_ALSO_ACTS_AS` в `helpers.js`, сверяет `tests/test_roles_manager_acts_as.py`), а НЕ правка кортежей `allowed_roles`. Поэтому сверка «роль ∈ разрешённых» — только через `role_allowed` (`_authorize`, `_has_role`, `can_transition`, очередь «Сегодня», ops-пинг) и `roleIn` во фронте; голый `role in (...)` с `warehouse_keeper`/`bookkeeper` обойдёт совмещение. Admin/boss-only права (себестоимость, прибыль, одобрение, подтверждение возврата) оно не даёт. Карточки «подтвердить сдачу/возврат» менеджер получает, только если активного носителя роли нет (`notify_recipients`). `/addrole` роли из `PAUSED_ROLES` не назначает; уже назначенные работают. **Откат** — очистить `ROLE_ALSO_ACTS_AS` (в обоих местах) и `PAUSED_ROLES`.
- Race-чувствительные операции (`mark_order_paid`, `confirm_payment`, `confirm_cash_deposit`) используют `SELECT ... FOR UPDATE` / advisory-lock — сохраняй паттерн.
- **«Заявлено по заказу» — ОДИН замок: строки заказов** (`services.debts.lock_orders`,
  по возрастанию id). Любая операция, которая меняет, сколько по заказу заявлено
  или зачтено (разбивка оплаты, «Получил деньги», сдача и её подтверждение,
  подтверждение/сторно платежа, подтверждение возврата, проверка отгрузки
  «оплаты сразу»),
  берёт его ДО `calc_claimable_cents`/`calc_order_balances` в той же транзакции.
  Свой advisory-lock у пути не годится: сдача сериализовалась «по менеджеру»,
  отметка оплаты — строкой заказа, разные замки друг друга не ждали, и одни
  деньги заявлялись дважды. Порядок замков — «заказ → платёж/строки склада»;
  отгрузка и отмена — advisory `ship:order` → строка заказа → склад.
- **Переход + его последствия — одной транзакцией.** Подтверждение платежа
  закрывает заказ в своей транзакции (`_close_order_if_covered_locked`),
  отмена заказа возвращает остаток в своей (`database.cancel_order` →
  `order_shipment.cancel_shipment_locked`; отказ склада — отказ отмены),
  возврат на доработку переводит заказ И заявку вместе
  (`reject_order_to_draft(..., req_id=)`), поступление по рассрочке закрывает
  сделку в своей (`machines._set_deal_closed_locked`). После коммита — только
  аудит и уведомления. Правка черновика перепроверяет `draft` в транзакции
  записи (`require_draft=True` у `add_order_item`/`remove_order_item`/
  `update_order_agent`/`update_order_currency`).
- **Тяжёлые списки — страницей в SQL.** `/api/orders` с `limit` читает
  `database.get_orders_page` (фильтры, LIMIT/OFFSET, total, pending_count —
  SQL; `_paginate_orders` — эталон семантики для тестов). Итоги продаж —
  агрегатами (`warehouse.sales_stats`, `shipment_counts_by_day`), а не по
  `list_shipments` (он обрезан). `IN (...)` по произвольному числу id — только
  пачками (`_IN_CHUNK`): у asyncpg предел 32 767 параметров. Период по
  `orders.created_at` пиши диапазоном по самой колонке, платежи за период —
  `status = 'confirmed' AND COALESCE(confirmed_at, created_at) …`: это формы
  индексов.

**LIKE-поиск по кириллице — только через `lower()`, и он переопределён В ОБОИХ
слоях.** Встроенный SQLite `LOWER()` ASCII-only («Иванов» так и остаётся
«Иванов»), Postgres — Unicode-aware. `database.get_conn` переопределял функцию
давно, `adb_core` — нет, и одинаковый на вид запрос вёл себя по-разному в
зависимости от того, синхронный слой его позвал или асинхронный: на проде
находил, локально нет, и тесты этого не ловили. Теперь регистрирует и
`adb_core._register_sqlite_functions`; сторож —
`tests/test_lead_calls.py::test_async_and_sync_paths_lowercase_cyrillic_the_same`.
Соединение туда передаётся УЖЕ открытым: `aiosqlite.Connection.__aenter__`
делает `await self`, и повторное ожидание того же объекта вешает поток намертво.

**Native async DB (asyncpg, задача #21):** денежное ядро (order/payment reads+writes, кредит, сдачи, возвраты) — на `services/adb_core.py` (asyncpg на проде / aiosqlite в тестах; `$N`-плейсхолдеры; `fetch/fetchrow/fetchval/execute`; `transaction()` CM с commit/rollback). Остаток (`get_setting/get_role/add_audit_log`, notifier) — sync, мостится через `async_db.__getattr__` (`asyncio.to_thread`; coroutine-функции пропускаются как есть). `_to_thread(db.X, ...)`-форма НЕ ловится grep'ом `db.X(` — аудитируй её при флипе функции в async.

**Оплата заказа — разбивка «как получены деньги» (`services/order_payments.py`,
схема `services/order_payments_schema.py`, фронт `webapp/static/payments.js` +
чистые хелперы `pay*` в `helpers.js`).** Требование владельца: «до отгрузки
менеджер вводит, как получил деньги — чтобы потом не возникало вопросов». Поток:
1. Менеджер оформляет заказ, выбирает «оплата сразу» / «в долг» → заявка.
2. Руководитель одобряет (в заявке — цена × количество = сумма по каждой
   позиции, итог и тип оплаты). Одобрение проводит расходную накладную (склад),
   заказ — `approved` («к отгрузке»). **Автоплатежа на всю сумму больше нет**: он
   заявлял деньги без способа, держал весь остаток «заявленным», и сдачи из-за
   него ложились «Заказы: —». Настройка `auto_ship_on_approve` кодом НЕ читается
   и читаться не должна: автоперевод в `shipped` пропустил бы ввод оплаты.
3. «Оплата сразу»: на карточке заказа «Внести оплату и отгрузить» (у кого есть
   отгрузка) / «Внести оплату» (автор). Форма — строки {способ cash/card/bank,
   валюта USD/UZS, сумма, курс, если валюта ≠ валюте заказа; по умолчанию ЦБ,
   правится}; первая строка предзаполнена суммой к оплате, «Ещё способ»
   подставляет остаток. Итог обязан СОВПАСТЬ с суммой к оплате
   (`payment_gap_cents`); меньше — отказ текстом («это уже „в долг“ — через
   доработку заявки»). Пересчёт округляет строку до цента: при строке в другой
   валюте допуск 1 единица базовой валюты, копейки берёт крупнейшая
   пересчитанная строка — сумма строк сходится с заказом до цента.
   **Сервер** (`database.mark_order_shipped`, под `lock_orders`) отказывает
   отгрузке «оплаты сразу» с `code=payment_required`, пока разбивка не покрывает
   заказ; `/api/orders/ship` отдаёт 409 с кодом (фронт открывает форму), бот
   `/ship` — тот же отказ с кнопкой в WebApp. «В долг» отгружается без денег.
   Старый pending-платёж без способа у «оплаты сразу» разбивка отклоняет
   («заменён»). Отгрузка ещё и отказывает, если списание склада при одобрении
   не прошло (`order_shipment.failed_at`): сначала повторяет списание, не вышло —
   `code=stock_not_written_off`.
4. Под каждую строку пишется ОДИН обычный `payments` в валюте заказа, строка —
   в `payment_parts` (1:1, UNIQUE payment_id). Долг, закрытие заказа,
   «Получено/Ждёт», дебиторка — прежний `services.debts`, второй формулы нет.
   Статус строки не хранится, выводится (`part_state`): `on_hand` (наличные у
   менеджера) / `in_deposit` / `awaiting_bank` / `confirmed` / `rejected`.
5. Карта/перечисление — подтверждает руководитель или бухгалтер
   (`/api/orders/confirm_payment`, `pay_ok`); **наличные этой кнопкой не
   подтверждаются** (`confirm_payment` → False) — только сдачей. Платёж
   отменённого/отклонённого заказа не подтверждается никогда.
6. Долг: каждое поступление — та же форма (`/api/orders/payment`, прежнее имя
   `/api/orders/mark_paid`); сумма без способа → 400. Часть долга законна.
7. «Сдать наличные» (`/api/deposits/create`: amount, currency, order_ids?;
   `/api/deposits/on_hand` — что на руках): FIFO по наличным строкам НА РУКАХ у
   сдающего (`cash_on_hand`: автор строки, платёж pending, нет живой сдачи) в
   валюте сдачи; строка берётся целиком, денег меньше — строка делится
   (`split_part_locked`: новая строка + новый платёж, `split_from`). Привязка —
   `cash_deposit_parts`. Остаток сдачи в базовой валюте — прежний FIFO по долгам
   без разбивки (`cash_deposit_orders`); не легло никуда — `unallocated_cents`
   (сдача создаётся, экран показывает). Валюта сдачи — `cash_deposit_currency`
   (нет строки = базовая: у `cash_deposits` колонки валюты нет). Подтверждение
   сдачи ОДНОЙ транзакцией подтверждает платежи её строк и закрывает покрытые
   заказы; отклонение возвращает строки «на руки» само (привязка живёт, пока
   сдача pending/confirmed). Наличные в живой сдаче отдельно не отклоняются.
8. Отмена одобренного заказа отклоняет ВСЕ его ожидающие платежи; если по заказу
   уже подтверждены деньги или наличные сданы — отказ отмены с текстом
   (`code=money_received`). Возврат «в счёт долга» больше долга
   (`calc_claimable_cents`) — отказ и при оформлении, и при подтверждении
   (`_debt_reduction_refusal`, `code=no_debt_to_reduce`): переплата клиента
   иначе исчезала.
Кто подтверждает — СЕРВИСНЫЙ рубеж `order_payments.confirm_rights` (зовут
`database.confirm_payment`/`confirm_all_pending_payments_for_order` — бросает
`PaymentError(403, code=confirm_forbidden)` — и `confirm_cash_deposit` —
`{ok: False, status: 403}`; HTTP и кнопки `pay_ok`/`dep_ok` получают отказ оттуда).
Менеджер (бухгалтер лишь через `ROLE_ALSO_ACTS_AS`) подтверждает свои и чужие
деньги ТОЛЬКО пока активных admin/boss/bookkeeper нет (`approval_mode='no_boss'`);
бухгалтер не подтверждает свои деньги при другом подтверждающем; руководитель,
внёсший сам, — да. Экран рисует кнопку по тому же правилу
(`server._money_confirmers`), пометка «руководителя/бухгалтера в системе нет»
(`self_note`, аудит) — из фактического наличия подтверждающих, не из роли.
**Свой курс** (разбивка `compute_parts`, бухгалтерия `resolve_rates`) — не дальше
`app_settings.manual_rate_max_deviation_pct` (10) % от курса ЦБ для всех ролей;
без курса ЦБ свой курс ставит только admin/boss (`accounting.manual_rate_refusal`).
«Долги» (`/api/debts`): «Оплата X ждёт подтверждения · после подтверждения долг:
Y» (`remaining_after_pending` = остаток − ждущее; `overpending` — ждущее сверх
долга после возврата), строки разбивки с состоянием, кнопка подтверждения — на
сумму карты/перечисления (`pending_confirmable`). «Поступления» (`get_money_totals`)
не считают подтверждённые наличные строки платежами — эти деньги уже в сдачах
(по валюте сдачи). Бухгалтерия (`accounting_enabled`) — отдельный путь: её
«Получил деньги» пишет платёж с документом журнала, такой платёж считается
«объяснённым» для отгрузки (`payment_gap_cents`). Данные до выката —
`python -m scripts.migrate_payment_breakdown` (dry-run по умолчанию). В e2e
`seed_order(payment_type="paid")` вносит разбивку картой сам (`pay=None` — нет),
форма — `conftest.pay_form`, сервисом — `conftest.pay_order`.

**«Куда поступили деньги» — карты и счета (`services/pay_accounts.py`, ручки
`/api/pay_accounts{,/create,/update,/archive}`, фронт — `payments.js` + чистые
`payAccount*` в `helpers.js`).** Требование владельца: выбрав «Карта» или «На
счёт», менеджер указывает, ЧЬЯ это карта / ЧЕЙ счёт; руководитель сверяет банк
по строке «на карту •••• 1234 (Фаридун М.)» / «на счёт ООО Farid Impeks (…6789)».
Что помнить:
- **Справочник — `acc_accounts` бухгалтерии** (вид card/bank, `holder`, `bank`,
  `card_last4`), реквизиты счёта — sidecar `acc_account_details` (20 цифр,

  нигде** — только 4 цифры; полный номер форма и сервер отвергают ТЕКСТОМ, а не
  обрезают. Валюта расчётного счёта — по коду в номере (000 — UZS, 840 — USD).
- **Ссылка — таблицами**: `payment_part_accounts(part_id PK → payment_parts,
  account_id)` и `machine_receipt_accounts(receipt_id PK → machine_payment_receipts,
  account_id)`; FK на `acc_accounts`, CHECK 4/20 цифр — `scripts/apply_constraints`.
  Удаление поступления чистит ссылку ПЕРВОЙ (`machines._delete_receipt_locked`).
  Деньги ходят и В ОБРАТНУЮ сторону: у выплаты поставщику счёт-ИСТОЧНИК лежит
  полем `supplier_payment_parts.account_id` (см. «Долги ПОСТАВЩИКАМ»), и он

- **Карта/перечисление без записи — 400** (`code=account_required`, «Строка N:

  `account_archived`). Проверка — в `order_payments.parse_parts`/`record_payment_parts`
  и `server._machine_receipt_account` (форма рассрочки и «оплачен» со способом).
  Старые строки без ссылки законны и подписываются как раньше;
  `require_account=False` — только разовый `scripts/migrate_payment_breakdown`.
- **Подпись одна** — `pay_accounts.destination_label` → `order_payments.part_label`
  («на карту •••• 1234 (Фаридун М.) · 7 130 USD»), `part_view.account_label`,

  «Долги», лента денег, пуш руководителю, дайджест, аудит, поступления рассрочки.
- **Тёзка не заводится**: та же карта (4 цифры + владелец без учёта регистра/точек/ё)
  или тот же номер счёта → `existed` с уже заведённой; архивная — 409 с текстом.
  Хвост карты/номер счёта у записи с деньгами не правится (`in_use`) — иначе
  старые платежи «переехали» бы на другую карту; владельца поправить можно.
- **Права**: завести — admin/boss/manager (из листа выбора, кнопкой под

  попадает, на старых платежах остаётся.
- **По умолчанию — последний выбор человека** (`pay_accounts.last_used`,
  выводится из его строк оплаты и поступлений; отдельной настройки нет).
- Бота не касается выбор: в боте нет потока, где выбирают карту/перечисление
  (`/pay` — платёж в кассу без способа), он только показывает подпись в карточке.

**Ежедневная сверка кассы (`services/cash_reconciliation.py`, схема —
`services/cash_reconciliation_schema.py`, ручки `/api/cash/reconcile{,/context,
/history}`, фронт — `webapp/static/cash_reconcile.js` + чистые `recon*` в
`helpers.js`, вкладка «Деньги → Сверка»; ряд вкладок раздела — см. «Вкладок в
разделе — не больше ЧЕТЫРЁХ»).** Требование владельца: «ежедневной
сверки кассы хватит… пишется и при нуле». Дыра, которую она закрывает:
`/api/deposits/on_hand` показывает деньги, которые КТО-ТО ВНЁС как оплату; если
менеджер оплату просто не завёл, расхождение не ловит НИЧТО. Физический
пересчёт — единственный способ это увидеть. Что помнить:
- **Своя таблица `daily_cash_counts`, а НЕ `acc_day_closes`.** У бухгалтерской
  строка стоит на `acc_accounts` (счёт кассы) и `acc_docs` (документ сверки), а
  «сколько должно быть» там = остаток по журналу `acc_entries`. При выключенном
  `accounting_enabled` журнал пуст и счетов нет — ожидаемое вышло бы нулём для
  любой кассы, а «включить только эту таблицу» значит завести счета и писать
  документы, то есть включить весь модуль. Здесь ожидаемое берётся из ЖИВОГО
  `order_payments.cash_on_hand`. Включат учёт — сверки не подерутся: разные
  таблицы и разные источники ожидаемого.
- **Одна строка на ВАЛЮТУ**, строки одного пересчёта склеивает `request_key`
  (он же ключ идемпотентности — партиальный UNIQUE по паре с валютой). Доллары
  и сумы не складываются: сумма по курсу — это переоценка, а не сверка, и
  недостача в 50 USD утонула бы в округлении миллионов сумов.
- **Пишется и при нуле.** «Записан пересчёт, расхождений нет» — тоже факт: без
  строки нельзя отличить «сверили, сошлось» от «сверку не делали». Повторный
  пересчёт за день законен (как у `acc_day_closes`); дубль режет только ключ.
- **Денег НЕ двигает.** Ни платежа, ни сдачи, ни долга не создаёт и не правит
  (сторож — `test_reconciliation_moves_no_money`). Примечание к расхождению
  ИНФОРМАЦИОННОЕ и необязательное: если бы «забыл занести оплату» заводило
  платёж, недостачу можно было бы объяснить текстом самому себе; а обязательное
  поле привело бы к тому, что расхождения перестали бы записывать вовсе.
  Подтверждения нет — это запись пересчёта, а не движение денег.
- **CHECK `diff_cents = counted_cents - system_cents`** (`scripts/
  apply_constraints`): разница хранится рядом (по ней идёт выборка
  руководителя), но соврать ею нельзя. `system_cents` — СНИМОК на момент
  пересчёта, а не ссылка на выборку: строки потом сдают в кассу, и через день
  тот же запрос дал бы другое число — расхождение «исправилось» бы само.
- **Права:** записать — admin/boss/manager (`ROLES_RECORD`), свою историю видит
  каждый, чужую — только руководство (`ROLES_SEE_ALL`); охват решает роль, а не
  флаг в теле запроса. Расхождения уходят в вечерний дайджест
  (`boss_digest`, блок `cash_counts`) БЕЗ порога `should_notify_now`: недостача
  в кассе — не «мелкое событие, которое подождёт».
- **Напоминание — пункт очереди дел «Сегодня»** (`work_queue`, severity `info`,
  `screen=money:reconcile`), а не пуш: сверка — просьба, а не блокирующее
  решение. Час — настройка `cash_reconciliation_reminder_time`, и она **ПУСТА
  по умолчанию = не напоминать**: экран и запись работают всегда, а пункт в
  очереди владелец включает, поставив час, когда решит, что привычка нужна.
  Само по себе напоминание приехало бы с выкатом и каждый вечер добавляло
  строку всем, кто про сверку ещё не слышал; очередь дел тем и ценна, что в ней
  нет лишнего. Побочно это снимает и зависимость тестов очереди от времени
  суток. Мусор в настройке гасит напоминание, а не подставляет свой час.
  Пустой ОСТАТОК напоминание не прячет: «по системе ноль, а в кармане деньги» —
  как раз то, что сверка обязана поймать.
- **Вкладка, а не кнопка внизу «Кассы», и НЕ за «Рабочими действиями»**: для
  руководителя пересчёт — контроль, а не работа склада, и список расхождений
  за переключателем не увидел бы ровно тот, ради кого он заведён. С ней ряд
  «Денег» занят ПОЛНОСТЬЮ: 4 вкладки и у менеджера (`confirm · debts · ops ·
  reconcile`), и у руководителя с работой (`debts · ops · reconcile · report`)
  — потолок ряда на 360dp, сторож — «ни одна РОЛЬ не получает больше 4 вкладок»
  в `helpers.test.js`. Следующий экран в «Деньгах» придётся вешать внутрь
  существующей вкладки.
- Тесты: `tests/test_cash_reconciliation.py`, `tests/e2e/test_cash_reconciliation.py`,
  `webapp/static/__tests__/cash-reconcile.test.js`; списки вкладок под роль —
  `test_boss_ui.py`, `test_cov_money.py`, `roles-acts-as.test.js`.

начиналось пустым, и менеджер набирал цену заново даже постоянному клиенту с
тем же товаром. Что помнить:
- **Приоритет один и живёт во фронте** (`helpers.priceSuggestions/pricePrefill`,

  клиента на ЭТОТ товар → `product_prices.sale_price` → пусто. Нечего
  подставить — поле остаётся пустым, ровно как до B7; ни один существующий
  поток от подсказки не зависит.
- **«Цена для постоянных клиентов»** (`product_prices.wholesale_price_cents`,
  колонка + `scripts/apply_legacy_columns`) сама НЕ префиллит: это альтернатива
  в один тап рядом с дефолтом. Признака «постоянный клиент» в проекте нет, и
  заводить его в v1 незачем — выбирает человек. Менеджер её ВИДИТ (в отличие от
  себестоимости): это подсказка ему.
- **Пол минимальной цены опускается до «для постоянных»**, когда она задана

- **Прошлая цена — `database.get_last_price_for_agent_product`**: товар по
  `order_item_products` (а не по имени — `product_href` товар не
  идентифицирует), контрагент по `orders.agent_id`, статусы —

- **Валюта важнее подсказки**: подсказка в другой валюте показывается, но не
  префиллит и не ставится тапом — 500 000 UZS в долларовом заказе это не
  подсказка, а ошибка на два порядка.
- Ответ приходит асинхронно и НЕ затирает набранное: префилл ставится, только

  `_text()`. openpyxl хранит строку с ведущим `=` как ФОРМУЛУ, и контрагент
  `=HYPERLINK(...)` выполнится у босса при открытии файла.
- Каждый `/api/*` endpoint → `_authorize(data, allowed_roles=..., rate_limit_scope=...)`. Default role для новых юзеров — `guest` (нулевые права).
- Telegram WebApp initData валидируется в `webapp/auth.py` через `hmac.compare_digest`.

**Локальный складской учёт (МойСклад удалён).** Остатки, каталог, контрагенты,
приход и расход — наши таблицы; интеграции с МойСклад в коде нет вовсе, и
возвращать её не надо. Что помнить:
- **Расходную накладную проводит только руководство** (`/api/wh/invoices/create`,
  `type=outgoing` → admin/boss; ОТМЕНУ накладной — и менеджер, пока выключен
  `delete_requires_boss`, но только СВОЕГО прихода: расход и чужую накладную
  отменяет руководство всегда, `server._invoice_cancel_allowed` + `can_cancel`
  в списке). Отгрузка клиенту идёт через заявку и
  одобрение: кредит-лимит, override, аудит. Прямой расход менеджером обходил
  весь контур — товар уезжал без заказа, без долга и без решения босса. Приход
  менеджеру оставлен (приёмка — его работа). Фронт переключатель «Расход» не
  показывает: вкладка/кнопка, которая гарантированно ответит 403, хуже
  отсутствующей — это же правило держит `clientsTabs` («Воронка» только
  руководству) и `moneyTabs` («Касса» без кладовщика).
- **Движение склада — только через `services/warehouse.py`.** Номер, шапка,
  строки и остатки пишутся ОДНОЙ транзакцией; остаток не уходит в минус;
  параллельные накладные по одному товару сериализуются `FOR UPDATE`, а
  позиции сортируются по `product_id` — иначе две накладные с составом [A,B] и
  [B,A] берут строки в обратном порядке и получают взаимный deadlock.
  Повторы одного товара схлопываются ДО проверки остатка.
- **Внутри чужой транзакции** зови `create_invoice_in` / `cancel_invoice_in`:
  они бросают `InvoiceError`, а не возвращают «не ок» словарём, который
  вызывающий спокойно закоммитит вместе со своими записями.
- **Отгрузка заказа** — `services/order_shipment.py`: одобренная заявка
  списывает товар расходной накладной, PDF собирает `services/invoice_pdf.py`.
  Идемпотентность по `order_shipment.order_id` (PK): повторное одобрение не
  спишет дважды. Не списалось — заказ помечается `failed_at` и попадает в
  дайджест «нужна доделка»; одобрение при этом не откатывается.
  **Печатная форма — ПОСЛЕ ответа, фоновой задачей.** `approve_shipment_request`
  по умолчанию (`pdf_delivery="background"`) коммитит отгрузку, отвечает боссу
  и отдаёт `pdf_task`; `deliver_shipment_pdf` рендерит weasyprint в потоке и
  шлёт документ менеджеру и боссу. Рендер (сотни миллисекунд CPU) и два вызова
  Bot API стояли на критическом пути одобрения — босс ждал бумагу, которая ему
  не нужна для решения. Задачи живут в `utils/background.py` (`spawn`:
  сильная ссылка + лог падения); в тестах `await res["pdf_task"]`, режим
  `"inline"` оставлен для случаев, где PDF нужен в том же вызове. Отказ PDF
  никогда не откатывает одобрение. То же в `invoice_delivery`: рендер в
  `to_thread`, иначе на время сборки встаёт весь event loop.
- **Приёмка контейнера** — `services/container_receipt.py`: приходная
  накладная. Повторная приёмка = ОТМЕНА прежней + создание новой одной
  транзакцией (количества правят сутки, и остаток обязан ехать за ними).
  Контейнер, оприходованный ещё в МойСклад (`received_at` есть, `invoice_id`
  пуст), к повторному приходу не допускается: его остаток приехал миграцией, и
  вторая накладная прибавила бы товар второй раз.
- **Резерв** локально — это одобренные заказы, ещё НЕ списанные накладной
  (`warehouse._reserved_by_product`; списанный уже уменьшил остаток, и резерв
  по нему вычел бы его второй раз). Доступное = остаток − резерв, и в каталог
  идёт именно доступное: обещать то, что уже обещано, — способ отгрузить дважды.
- **Границы периода в аналитике.** `invoices.invoice_date` — ДАТА, а границы
  приходят моментами. Полуинтервал с обрезкой до дня ломает «сегодня» (начало
  дня и «сейчас» дают одну дату), поэтому верхнюю границу считает
  `warehouse._upper_bound`: полночь исключаем, любое другое время включаем.
- **Идентификаторы.** Колонки `orders.agent_id`, `credit_limits.agent_id`,
  `leads.agent_ms_id`, `machine_deals.agent_ms_id`, `product_prices.ms_id`,
  `product_photos.ms_id` остались текстовыми с эпохи МойСклад, но хранят теперь
  НАШИ id строкой — их переписал `database.backfill_local_identifiers`.
  Переименовать колонку нечем (инкрементальных миграций в проекте нет), а
  таблица-двойник ради имени поля хуже. Там, где имя врало по существу
  (`order_items.product_href` — это ссылка на документ), связь уехала в
  отдельную таблицу: `order_item_products`, `container_item_products`.
- **Перенос ИСТОРИИ — `scripts/migrate_history_from_moysklad.py`**, отдельно от
  переноса справочников. Главное про него: он **НЕ ДВИГАЕТ ОСТАТКИ**. `stock`
  приехал снимком на сегодня и все исторические отгрузки уже включает, поэтому
  строки `invoices`/`invoice_items` пишутся НАПРЯМУЮ, мимо
  `services/warehouse.py` — единственное такое место в проекте. Провести их
  через warehouse значит списать весь оборот компании второй раз. Сторож —
  `tests/test_migrate_history.py::test_migration_never_moves_stock`.
  Идемпотентность — по родным `orders.ms_customerorder_id` /
  `payments.ms_paymentin_id`, номера накладных — своей серией `MS-D-*` мимо
  `invoice_counters`. Несопоставленное (отгрузка без заказа, платёж без
  основания, позиция без карточки) не угадывается и не пропускается молча —
  уходит в отчёт категорией для ручного разбора.
  Закупочная сторона переносится тем же прогоном: `entity/supply` → приходные
  накладные (`MS-S-*`), `entity/paymentout` → **`supplier_payments`**, а НЕ
  `payments`: там деньги ОТ клиентов, на них считается вся дебиторка, и
  исходящий платёж уменьшил бы долг клиента на сумму, выплаченную поставщику.
  Аванс поставщику (выплачено > поставлено) расхождением НЕ считается — это
  обычная практика, и помечать её значит топить настоящие проблемы в шуме.
  **Заказ покупателя в этом аккаунте — редкость** (боевая выгрузка: 26 заказов
  против 421 отгрузки и 326 платежей). Продажу оформляют сразу отгрузкой, а
  деньги — платежом без документа-основания, поэтому: отгрузка без заказа
  СТАНОВИТСЯ заказом (идемпотентность по `orders.ms_demand_id`), а платёж без
  основания гасит долг СВОЕГО контрагента по FIFO, от старых заказов к новым —
  как `create_cash_deposit` для сдач. Это СОГЛАШЕНИЕ, а не факт из МС, поэтому
  помечено в комментарии каждой строки и валюта обязана совпадать (конверсии
  при закрытии заказа нет). Платёж делится между заказами отдельными строками:
  `order_id` одно поле на строку, у частей `ms_paymentin_id` получает суффикс
  `#N`, сумма частей равна сумме платежа. Контрагент при этом НЕ угадывается —
  платёж без него или без непогашенных заказов остаётся в отчёте.
  Разбор одного заказа построчно — `--explain <номер>` (только чтение).
  **Валюта — `rate.currency.isoCode` (expand), курс — `rate.value` документа**
  (к учётной валюте МС из `entity/currency`, `default=true`), приведённый к
  семантике `fx_rate_to_base`; учётная ≠ BASE_CURRENCY → звено из
  `currency_rate_daily` на дату. Курс, не подтверждённый справочником (в 20+
  раз от его `rate`), неизвестная валюта, дыра в архиве — `MigrationStop` ДО
  записи, и в `--dry-run` тоже. `name` у валюты МС — «сум», не ISO.
  **Моменты МС — московские** (`Europe/Moscow` → бизнес-зона через zoneinfo):
  вечерний документ в Ташкенте уже следующего дня/месяца.
  **Ключ исторической накладной — UUID документа** в
  `ms_id_map(entity_type='demand'|'supply')`; номер только отображение, дубль
  имени МС получает суффикс `-2`. Контрагенты только с закупками → `supplier`.
  **Историю не отменяют**: `warehouse.cancel_invoice_in` отказывает накладной
  с номером `MS-D-/MS-S-` или ключом в `ms_id_map` (`historical_invoice_sql`),
  `cancel_order_full` — заказу с `ms_demand_id` или исторической отгрузкой
  (`order_shipment.historical_cancel_refusal`). Склад по ним не двигался, и
  откат вернул бы товар, давно уехавший к клиенту. Заказ МС без отгрузки
  отменять можно — склад он не трогал, а отмена снимает резерв. Накладная
  прихода по возврату (`return_receipt`) напрямую не отменяется — только
  возвратом.
- **`scripts/migrate_from_moysklad.py` живёт со СВОИМ клиентом МС.** Он обязан
  пережить удаление интеграции — иначе перенос перестанет воспроизводиться
  ровно тогда, когда ещё может понадобиться (аккаунт МС живёт месяц-другой
  после переключения). `ms_id_map` держим по той же причине.
  **Повторный `--apply` после переключения отказывает**: остаток пишется
  снимком, и живые накладные (после `MIN(ms_id_map.migrated_at)`, не из серии
  истории) или заказы с `user_id <> 0` были бы стёрты. `--i-know-live-data`
  обновляет справочник, но остаток товаров с живыми движениями не трогает.
  `migrated_at` повтором не сдвигается — это и есть граница «до/после».

**Списание с причиной и инвентаризация (`services/inventory.py`, ручки
`/api/stock/writeoffs*` и `/api/stock/counts*`, фронт — «Склад → Движения →
Списания»).** Ответ на «пересчитали, не сходится» и «разбилось/пропало»: до
этого остаток менялся только приходом, отгрузкой, приёмкой и возвратом, и
расхождение либо оставалось навсегда, либо его выправляли накладной без
причины. Что помнить:
- **Товар двигает ОБЫЧНАЯ накладная склада**: списание — расходная, излишек —
  приходная, обе через `warehouse.create_invoice_in`. Своего движения остатка в
  модуле нет ни строки — вместе с `_apply_stock_delta` бесплатно достаются
  блокировки `FOR UPDATE`, схлопывание повторов, отказ «остаток не в минус» и
  хук себестоимости. То же решение, что у приёмки контейнера, и оно же держит
  инвариант сценариев «остаток = приходы − расходы по действующим накладным».
- **`stock_writeoffs` — sidecar к накладной**: причина (обязательна, свободный
  текст; `QUICK_REASONS` — только подсказки формы), фото, сессия пересчёта,
  себестоимость потери. `kind='surplus'` — та же лента: излишек это тот же
  результат пересчёта, и смотреть его надо рядом со списанием.
- **Фото уезжает ДО проведения** (`/api/stock/writeoffs/photo` → `file_id`,
  форма несёт его в `create`): записи, к которой его прицепить, в момент съёмки
  ещё нет, а держать мегабайты base64 в теле списания незачем. Хранилище — тот
  же приватный канал, что у техники и товаров (`PHOTOS_TG_CHAT_ID`); нет
  переменной — `can_photo: false`, кнопки нет, остальное работает. Показ —
  `/api/stock/writeoffs/photo_view` со скоупом по НОМЕРУ ЗАПИСИ: `file_id` от
  клиента вытянул бы из канала любой чужой файл, а прямая ссылка Telegram
  содержит токен бота.
- **Списание — не продажа.** Цена позиций 0, и накладная списания ИСКЛЮЧЕНА из
  выручки (`warehouse._shipments_where` через `not_writeoff_sql`) и из отчёта о
  прибыли (`costing.period_report`). Иначе отчёт продаж получил бы отгрузки на
  нулевую сумму (число отгрузок и клиентов вверх, средний чек вниз), а прибыль
  показала бы убыточную «сделку» на всю себестоимость. Себестоимость при этом
  фиксируется штатным FIFO — она и есть цена потери — и кладётся в
  `stock_writeoffs.cost_cents` (учёт выключен → NULL, и всё работает как
  раньше). Наружу она идёт только `costing.COST_ROLES`, режется В ОТВЕТЕ.
- **Дельта пересчёта считается в момент ПРОВЕДЕНИЯ**, от живого остатка под
  блокировкой, а не от запомненного при вводе: человек считает склад полчаса, и
  параллельная отгрузка иначе превратилась бы в недостачу. Строка пересчёта —
  это ФАКТ («на полке 7»), остальное выводится.
- **Пересчёт применяется целиком или никак**: все строки сессии — одной
  транзакцией (`inventory.apply_count`), идемпотентность двойная — CAS по
  статусу сессии и ключ ручки, который пишется ТОЙ ЖЕ транзакцией
  (`_Idem(..., atomic=True)` + `database.idem_store_in`). Открытая сессия по
  складу одна: две параллельные применили бы одну и ту же дельту дважды.
- **Сторно — отмена той же накладной** (`cancel_invoice_in`) плюс отметка
  `cancelled_at`, а не «обратное списание»: два документа на один факт хуже
  честного «этого не было». Окно у автора — сутки (`VOID_WINDOW_HOURS`, как
  окно правки приёмки), дальше и чужое — руководителю; сверху действует общий
  `delete_requires_boss`. Накладную списания `/api/wh/invoices/cancel` не
  отменяет вовсе (`linked_writeoff`) — иначе запись о причине осталась бы жить
  без движения товара.
- **Права — как у приёмки контейнера, а не как у расходной накладной.** Расход
  клиенту проводит только руководство (заявка, лимит, решение); здесь товара
  просто нет физически, и запрет означал бы, что менеджер обязан держать в
  системе остаток, которого на полке не видит. Контроль — лента с причиной,
  автором и временем плюс аудит (`stock_writeoff`, `stock_count_apply`).
- **Фронт — второй уровень вкладки «Движения»**, а не пятая вкладка раздела:
  их потолок — четыре (`helpers.test.js`), а отдельного раздела списание не
  заслуживает. Ряд `.seg` внутри вкладки — тот же приём, что у фильтра долгов;
  каркас (шелл + переключатель) входит в КАЖДУЮ ветку через `whFrame`
  (UI-BUG-04). Товар начинают с ВЫБОРА (`openCatalogPicker`).

**Несколько складов (B8, `services/warehouse.py` + `/api/warehouses/*`,
`/api/stock/transfer{,s}`).** Схема (`warehouses`/`stock(warehouse_id)`) была
готова с начала, но сидинг заводит один склад — компания пока физически в
одной точке. Раздел добавляет управление и перемещение, НЕ трогая
однoскладской случай ни на бит:
- **Архив — sidecar `warehouse_archived`**, а не колонка `warehouses.archived`
  (инкрементальных ALTER в проекте нет). Строка есть → склад не предлагается
  в форме (`list_warehouses(include_archived=False)`), но остаётся в истории.
  Архивировать можно только пустой склад (`quantity <> 0` по нему — отказ
  `nonzero_stock`) и не последний активный (`last_active_warehouse`) — иначе
  накладную провести стало бы некуда.
- **`default_warehouse_id()`** теперь берёт MIN(id) СРЕДИ АКТИВНЫХ (деградирует
  к MIN(id) вообще, если архивны все) — старое поведение с одним складом не
  меняется, потому что архивных складов там нет вовсе.
- **Перемещение (`transfer_stock`)** — одна транзакция, тот же инвариант, что у
  накладных: обе строки `stock` блокируются в порядке `sorted(warehouse_id)`
  (без него встречные [A→B]/[B→A] ловят deadlock на Postgres), нехватка
  остатка откатывает всё перемещение, история — `stock_transfers`
  (sidecar, FK/CHECK `quantity > 0` и `from ≠ to` — `scripts/apply_constraints`).
- **Каталог**: `/api/stock` отдаёт `by_warehouse` и корневой `multi_warehouse`
  ТОЛЬКО когда активных складов больше одного (`webapp.server.api_stock`); при
  одном складе форма ответа не получает ни одного нового поля — байт-в-байт
  как раньше. Фронт то же самое: строка `.stock-by-warehouse` рисуется, только
  если `stockData.multi_warehouse`.
- **Заказ**: склад отгрузки — sidecar `order_warehouse` (PK `order_id`),
  `order_shipment.ship_order` берёт его через
  `warehouse.resolve_order_warehouse()` (выбор менеджера, если есть, иначе
  `default_warehouse_id()`). Пикер в редакторе заказа и в форме накладной
  показывается, только если `/api/me` вернул `multi_warehouse: true`
  (`active_warehouse_count() > 1`) — иначе ни одного похода в
  `/api/warehouses/active` и ни одной лишней кнопки.
- **Права**: справочник складов (`/api/warehouses/{list,create,rename,archive,
  unarchive}`) — admin/boss-only, «Настройки → Склады». Выбор активного склада
  и перемещение (`/api/warehouses/active`, `/api/stock/transfer{,s}` кроме
  истории) — и менеджеру: он физически двигает товар и создаёт накладные так
  же, как приход. История перемещений — руководству.
- Тесты: `tests/test_multi_warehouse.py` (в т.ч. `test_single_warehouse_*` —
  явно держит инвариант «один склад → поведение не меняется»),
  `webapp/static/__tests__/multi-warehouse.test.js`.

**«Счёт» — документ клиенту ДО отгрузки (`services/sales_invoice.py`, ручки
`/api/orders/invoice{,/print,/send}`, печатная форма —
`invoice_pdf.build_sales_invoice_html`, фронт — `openSalesInvoiceSheet` в
app.js + чистый `salesInvoiceAvailable` в `helpers.js`).** Жалоба владельца:
печатная форма появлялась только ПОСЛЕ отгрузки (`order_shipment` →
`render_invoice_pdf`), то есть разговор с клиентом шёл задом наперёд —
сначала отдай товар, потом покажи бумагу. Что помнить:
- **СЧЁТ НИЧЕГО НЕ ДВИГАЕТ.** Ни остатка, ни накладной, ни платежа, ни долга,
  ни статуса заказа; в выручку и отчёты не попадает. Модуль состоит из
  ЧТЕНИЯ, единственная запись — строка аудита (`sales_invoice_printed` /
  `sales_invoice_sent`, её пишет ручка). Сторож —
  `test_sales_invoice.py::test_building_and_printing_the_invoice_moves_nothing`
  (снимок склада, накладных, платежей и заказов до/после).
- **Номер счёта = номер заказа, дата = дата заказа.** Своей
  последовательности нет намеренно: `invoice_counters` нумерует СКЛАДСКИЕ
  накладные, и бумага, по которой товар не двигался, делала бы в них дырки; а
  счётчик выдал бы на один заказ три номера при трёх печатях, и второй
  экземпляр перестал бы быть тем же документом.
- **Кнопка — с момента, когда есть что показать**: выбран клиент и заведена
  хотя бы одна позиция, то есть ещё на ЧЕРНОВИКЕ, до заявки. После отгрузки
  остаётся (копия счёта). Отменённый и отклонённый заказ счёта не получают.
  Менеджеру — по своему заказу, руководителю — любой и за «Рабочими
  действиями» (это работа менеджера, как «Отгрузить»).
- **Движок один** — `services/invoice_pdf.py` (WeasyPrint, те же `_CSS` и
  шрифты, что у накладной): второй печатный движок разошёлся бы с первым на
  первой же правке, и клиент получал бы от одной компании две разные по виду
  бумаги. Сумма прописью — `services/numerals.py` (num2words сознательно не
  используется, см. его докстринг), реквизиты — `app_settings.company_*`
  через `documents.company_requisites`; незаполненный реквизит просто не
  печатается, блокировать счёт из-за пустого поля нельзя.
- **«Отправить PDF» шлёт СОСТАВИТЕЛЮ**, а не клиенту напрямую (в отличие от
  расходной накладной — `invoice_delivery`): счёт обсуждают, менеджер
  пересылает его сам, когда договорился; у большинства контрагентов Telegram
  не привязан вовсе, и «отправить клиенту» отвечало бы отказом чаще, чем
  работало. Печать — общий путь CUPS (`printing.print_pdf_bytes`), без
  `cups-client` кнопки нет (`can_print` в ответе `/api/orders/invoice`).
- Тесты: `tests/test_sales_invoice.py`, `tests/e2e/test_sales_invoice.py`,
  `helpers.test.js` («когда кнопка есть на карточке») и блок «карточка заказа:
  кнопка „Счёт“» в `app-load.smoke.test.js`.

**Печать на офисный принтер (`services/printing.py` + `handlers/printing.py`).**
CUPS стоит на хосте, в контейнере только КЛИЕНТ (`cups-client`: `lp`,
`lpstat`), адрес — в `CUPS_SERVER`. Что помнить:
- **Печатаем ПО КНОПКЕ, не автоматически.** Половина печатных форм уходит на
  проверку перед отправкой клиенту; печатать их все — переводить бумагу.
- **Печать НИКОГДА не роняет основной поток.** Накладная проведена, документ
  ушёл в Telegram — отказ принтера обязан стать сообщением «не напечаталось,
  вот почему». Ни одна функция модуля не бросает: всё в `PrintResult`.
- **Причина отказа — текстом.** `bool` не даёт сказать, что случилось, а
  «Ошибка» отправляет менеджера искать админа. Типовые ответы CUPS
  переводятся в понятные фразы (`_KNOWN_ERRORS`), сырой хвост — в `detail`.
- **`ok` значит «задание принято ОЧЕРЕДЬЮ», а не «бумага вышла».** Поэтому в
  чат пишем «отправлено на печать», а проверить принтер можно `/printer`
  (`lpstat -p`) — ровно для случая «бот сказал „отправлено“, а бумага нет».
- **В callback_data — ТИП и ID, а не путь к файлу.** Путь не влезет в 64
  байта и позволил бы напечатать любой файл контейнера. PDF пересобирается в
  момент нажатия (`invoice_id` → `warehouse.get_invoice` → `render_invoice_pdf`):
  документ заведомо актуален и не зависит от того, пережил ли файл рестарт.
  Формат callback'а — в `printing.invoice_callback/parse_callback`, чтобы
  producer (`order_workflow._print_keyboard`) и хендлер не разъехались.
- **Нет `cups-client` — нет кнопки** (`printing.is_available`): кнопка,
  которая гарантированно ответит отказом, хуже отсутствующей.
- **Асинхронно.** `subprocess.run` заблокировал бы event loop на время
  разговора с CUPS (а он идёт по сети), поэтому
  `asyncio.create_subprocess_exec`, как у LibreOffice в `legal_docs`.
- **Печать есть и в WebApp** (`/api/wh/invoices/print`, `/api/docs/print`):
  список накладных и документов отдаёт `can_print`, и без `cups-client`
  кнопки в интерфейсе нет — правило то же, что у бота. Ручка отвечает
  `PrintResult.message`/`error` текстом, фронт показывает его тостом.

**Юридические документы в WebApp (`services/documents.py`, «Продажи →
Документы»).** Движок `legal_docs` (docxtpl → LibreOffice) был без входа: ни
команды, ни ручки — расписку негде было составить. Теперь форма в WebApp
(`/api/docs/create`, роли admin/boss/manager) → PDF → Telegram составителю с
кнопкой «Распечатать» (`prn:doc:<id>`) → печать из WebApp или бота. Что помнить:
- **Реквизиты компании — в `app_settings` (`company_*`)**, ставит руководство
  (`/api/docs/company/set`); форма показывает их и даёт поправить для одного
  документа, а без `company_name` создание отвечает 400 текстом.
- **Файл хранится** (`DOCUMENTS_DIR`, том `/app/data`), печать и повторная
  отправка ЧИТАЮТ его, а не пересобирают: расписка подписана один раз, второй
  рендер с новой датой — другой документ. Файл пропал — ручка говорит об этом
  текстом, а не рендерит молча заново. Путь наружу не выходит (`file_exists`).
- Доставка и печать НИКОГДА не откатывают созданный документ — как у накладной.
- Ошибки формы — `DocumentError` → 400 с текстом, показывается внутри формы.
- Рендер мокается на границе: `documents.render_pdf` (LibreOffice), тест с
  настоящим `soffice` пропускается без бинаря (`tests/test_documents_api.py`).

**Кредит-лимиты (энфорс):** при одобрении credit-заявки `approve_shipment_request(..., override)` считает `check_credit_limit`; при превышении возвращает `needs_override` и НЕ одобряет → босс жмёт «Одобрить с превышением» (`req_ovr:` / webapp `override=true`), это ставит `orders.credit_limit_override` + audit. `get_agent_current_debt` считает долг батчем (items/payments/returns), без N+1.

**Скидка к прайсу по обычному заказу (`services/order_discounts.py`).** У сделки
по технике руководитель видит «24 000 USD · прайс 25 000 USD · скидка 4%», у
заказа видел только введённую цену. Теперь то же считается по строкам заказа.
Что помнить:
- **Эталон — `product_prices.sale_price_cents`**, и только в валюте заказа:
  прайс не переоценивают каждый день, и «пересчитанная по курсу» скидка была бы
  выдумкой. Валюта не та или прайса нет — строка идёт с прочерком, а НЕ со
  «скидкой 0%» (это означало бы «продали ровно по прайсу», которого нет).
- **Скидка нигде не хранится** — выводится при показе: колонка `discount_pct`
  устарела бы при первой правке прайса. История решения — `audit_log`
  (`discount_approved`, пишется в момент одобрения).
- **Средняя по заказу взвешенная** (по суммам прайса с учётом количества), а не
  среднее арифметическое процентов.
- **Порог — `app_settings.order_discount_requires_approval_pct`** (15; `0` —
  выкл.). Скидка ≥ порога по ЛЮБОЙ строке или в среднем помечает заявку и
  требует ЯВНОГО второго нажатия одобряющего — `approve_shipment_request(...,
  discount_ack)` отвечает `needs_discount_ack` ровно как кредит-лимит отвечает
  `needs_override` (бот: кнопка `req_dsc:`, она передаёт ОБА флага — заявка
  может пробить оба порога, и раздельные подтверждения гасили бы друг друга;
  webapp: `discount_ack=true`). Нового «нельзя отгрузить» скидка НЕ создаёт:
  каждый заказ и так проходит одобрение руководителя, а второй шлагбаум спорил
  бы с `payment_required` из `order_payments` — состояние остаётся одно.
  Менеджер видит причину строкой (`pending_note` → `discount_note` в
  `/api/orders` и в ответе `/api/orders/submit`), в стиле `payment_required`.
- **Сравнить сегодня почти нечего**: `/api/orders/add_item` держит тот же
  `sale_price` ЖЁСТКИМ минимумом («Цена ниже минимальной»), поэтому позиция
  дешевле прайса через ручку не заводится. Скидка возникает, когда прайс
  подняли ПОСЛЕ заказа, позиция приехала миграцией или цену задали позже.
  Станет прайс «рекомендуемой ценой» (ветка price-lists) — этот слой заработает
  в полную силу, менять его для этого не придётся.
- Прайсы читаются БАТЧЕМ на весь список (`load_reference_prices`) — в «Заявках»
  и «Заказах» N+1 уже чинили. Подписи — одни на бот и WebApp: `line_label`/
  `summary_label`/`flag_label` в сервисе, `discountLineSuffix`/
  `discountBlockHtml`/`discountPendingNote` в `helpers.js` (второй формулы
  скидки во фронте нет — он получает готовые проценты).
- **Где видно.** Бот: карточка «Новая заявка» (хвост строки + сводка + пометка)
  и отдельное сообщение с кнопкой `req_dsc:`. WebApp: «Решения»
  (`requestCardsHtml` — хвост строки и блок `credit-ctx`) и список заказов
  (`renderOrdersMain` — тот же хвост строки плюс `discount_note`, пока заявка
  ждёт). Прайс менеджеру не секрет: `sale_price` он и так видит в каталоге,
  себестоимость по-прежнему только руководству.

**Техника (волна 4):** `machines/machine_hours/machine_photos/machine_deals` —
единственная часть схемы с FOREIGN KEY (связи строго иерархические). На SQLite
FK не энфорсятся, поэтому `services.machines.delete_machine` чистит детей явно.
Себестоимость (`cost_cents`) режет `visible_machine` в СЕРВИСЕ, не на фронте —
иначе любой новый вызов вернёт её обратно. Моточасы: история в `machine_hours`,
последнее значение дублируется в `machines.hours`; показание меньше предыдущего
отвергается (опечатка), откат — только boss через `force=True`. Фото храним
`tg_file_id` + обязательный `file_unique_id` (переживает смену сервера Bot API,
tg_file_id — нет). VIN нормализуется (upper, без пробелов/дефисов) перед
записью, длина НЕ фиксируется 17 символами — у корейской техники серийники
другие. **Решение (волна 7): остаёмся на облачном Bot API**, локальный сервер
не поднимаем — `file_id` привязан к паре «бот + сервер», переезд обнулил бы все
`tg_file_id`; фиксируем сейчас, пока таблица пустая.

**Техника в WebApp (раздел «Заказы → Техника»).** Формы, фотографии и сделки —
в WebApp (`/api/machines/*`), в боте остались просмотр и `/hours`. Что помнить:
- **Граф переходов статуса — один**, `machines.NEXT_STATUSES` / `next_status_options`
  (подпись зависит от ПАРЫ статусов: «Прибыла» и «снять бронь» ведут в один
  `in_stock`). Проверяется он **в ручке**, а не в `set_status`: внутренние
  вызовы (`create_deal`, `close_deal`) двигают статус в обход ручного графа
  законно. Продажи/рассрочки в графе нет — им нужны цена и покупатель. Пока у
  машины живая заявка на сделку, ручка отвечает 409 (`pending_refusal`).
- **«Прибыла» — отдельная ручка `/api/machines/arrive`, открытая менеджеру**
  (`machines.mark_arrived`: CAS `in_transit → in_stock` + локация одним UPDATE,
  аудит `machine_arrived`, ключ идемпотентности). `/api/machines/status` — только
  руководству, и у менеджера на машине «в пути» не было ни одной кнопки, кроме
  моточасов. Карточка отдаёт `can_arrive`; руководству тот же переход второй
  кнопкой не рисуется.
- **Роль режется в слое чтения**, как себестоимость: `visible_machine`
  (`cost_cents`) и `visible_deal` (`buyer_passport`). На запись — тоже: что
  менеджер не видит, того он и не задаёт (иначе поле возвращается через форму).
- **`tg_file_id` наружу не выходит.** Файловый URL Telegram содержит токен
  бота, поэтому фото проксируются `/api/machines/photo`; `photo_id` ищется
  среди фото заявленной машины (гейт от подстановки чужого id), кэш — по
  `file_unique_id`. Текст ошибки Bot API логируй через `utils.helpers.redact_token`.
- **Загрузка — base64 в JSON**, не multipart: `python-multipart` в зависимостях
  нет, `UploadFile`/`Form` без него роняют приложение на старте. Тип проверяем
  по сигнатуре байтов, не по mime из data-URL. Канал-хранилище —
  `MACHINE_PHOTOS_TG_CHAT_ID`; без него загрузка выключена (`can_upload_photo`
  в ответе карточки), фото по-прежнему шлют боту.
- Ручки пиши **в `webapp/server.py`**: `scripts/gen_role_matrix.py` парсит
  `allowed_roles` только оттуда (константы вроде `_MACHINE_ROLES` он резолвит).
- **VIN правится отдельной функцией** `change_vin`, а не полем в whitelist
  `update_machine_fields`: у него нормализация и проверка уникальности. Ручка
  `/api/machines/update` вызывает её ПЕРВОЙ — иначе при занятом серийнике
  карточка осталась бы изменённой наполовину. Удаление (`/api/machines/delete`)
  отказывает машине со сделкой или живой заявкой: продажа — денежный факт,
  такие уводят в архив. Решённые заявки без сделки уходят вместе с карточкой.
- **Марки, модели и контейнера в форме машины нет**: первые два входят в
  название, контейнер — отдельная сущность. У старых карточек поля остались,
  карточка показывает их, только если заполнены.

**Сделки по технике — через одобрение (`services/machine_deal_requests.py`).**
Решение владельца: бронь, продажу и рассрочку оформляет менеджер, руководитель
одобряет. Что помнить:
- **Заявка — отдельная таблица `machine_deal_requests`, а не статус сделки.**
  `machine_deals` получает строку только при одобрении (`deal_id` в заявке),
  поэтому дебиторка, напоминания, бухгалтерия и архив, читающие
  `machine_deals`, заявок не видят, а старые сделки — одобренные по построению.
  График рассрочки строится в день ОДОБРЕНИЯ (`machines.insert_deal_locked`).
- **Машина на время заявки статус не меняет** (CHECK `machines_status_chk` без
  ALTER не расширить): «ждёт одобрения» выводится из живой заявки
  (`pending`/`rework`), отклонение машину не трогает — «вернуть прежний статус»
  нечего. Вторую живую заявку на машину держат `machines.lock_machine` +
  `active_request_locked` в транзакции записи и частичный UNIQUE
  `idx_machine_deal_requests_active`; прямая сделка руководства
  (`create_deal`), ручной переход статуса и удаление машины при живой заявке
  отвечают отказом. Порядок замков — «машина → заявка».
- **Кто решает:** admin/boss; менеджер — только пока активных admin/boss нет
  (`decision_rights`, зеркало `_money_confirmers`), тогда `approval_mode =
  'no_boss'`, экран и аудит говорят «руководителя в системе нет». Совмещение
  ролей права решать не даёт. Заявка руководства одобряется сразу той же
  транзакцией (`approval_mode = 'auto'`), ответ `/api/machines/deal` прежний
  (`deal_id`, `status`, `payments`); у менеджера — `pending: true`.
- **Карточка решения** (`notify_decision_card`, всегда сразу — это решение,
  не сводка) уходит `tg_send_message`'ом с кнопками `mdr_ok/mdr_no/mdr_rw`
  (`utils.keyboards.machine_request_keyboard`); хендлеры — `handlers/machines.py`
  по правилам «Кнопки карточек» (исход неактивной кнопкой, устаревшая карточка
  гасится `_settle_stale_machine_request`, причина доработки — force_reply).
  Итог менеджеру — `notify_outcome`. Паспорт в заявке режет `visible_request`.
- **На доработке** машина остаётся за заявкой; править и отправлять снова может
  только автор (`resubmit`, пустой паспорт оставляет прежний), отозвать —
  автор или руководство (`cancel`). Рассрочке паспорт обязателен.
- **Рассрочку ведёт менеджер**: `/api/machines/receipt` и `/payment` (отметка
  «оплачен») открыты ему, поступление несёт способ `cash/card/bank`
  (`machines.RECEIPT_METHODS` = ключи `order_payments.METHODS`, sidecar
  `machine_receipt_methods`; форма требует, кнопка «оплачен» — нет). Подтверждения
  у поступлений по рассрочке нет (это факт, а не заявка, как было). Стереть деньги
  (`/receipt_delete`, снятие отметки, отмена документа бухгалтерии) — руководство,
  менеджер только без руководителя (`_machine_money_undo_mode`, аудит).
- **Снять бронь** (`/api/machines/unreserve`, `mdr.unreserve`): менеджер — свою
  одобренную бронь, любую — только без руководителя (`no_boss`); остальные
  ручные переходы — `/api/machines/status`, руководству. Снятая бронь →
  `released` (и когда снял руководитель): старая бронь не даёт права снять
  следующую.
- CHECK вида/статуса/режима и «одобренная продажа ссылается на сделку» —
  `scripts/apply_constraints` (значения из модуля), FK — в DDL, как у всей
  техники. Во фронте заявки — группа `machine_deals` экрана «Решения»
  (`registerDecisionGroup`, карточки `machineRequestCardHtml`/
  `wireMachineRequestActions`), пункт `machine_deals` очереди «Сегодня»
  руководителя (`work_queue`, адрес `decisions` → общий бейдж) и список над
  «Складом → Техникой» (`renderMachineDealDecisions`). Кнопки решения
  (одобрить/отклонить/на доработку) — по `can_decide` и за «Рабочие действия»
  НЕ прячутся; оформление брони/продажи/рассрочки, поступления и снятие брони —
  работа, у руководства за выключателем.

**Удаление — выключатель `app_settings.delete_requires_boss`** (по умолчанию
выкл.: «пока может и менеджер, в будущем только руководитель»). Одна проверка
`server._require_delete_right` на все ручки удаления (`/api/machines/delete`,
отмена накладной `/api/wh/invoices/cancel`); флаг едет в `/api/me` (один
источник — `server._delete_requires_boss`), фронт прячет кнопки ОДНИМ
`deleteActionsVisible()` (+ `can_delete` карточки / `canCall` ручки).
Переключает руководство выключателем «Удаление — только руководитель» в
«Настройках» рядом с «Рабочими действиями» (`deleteSwitchHtml`,
`/api/settings/delete_requires_boss`, аудит `setting_changed`). Ручки удаления ТОВАРА в проекте нет — появится, звать тот
же `_require_delete_right`.

**Рассрочка: план и факт — разные вещи.** График (`machine_deal_payments`) это
план, поступления (`machine_payment_receipts`) — факт. Клиент платит не «платёж
№3», а деньги: в один месяц больше, в другой меньше, поэтому поступления копятся
общей суммой и гасят график по порядку (`machines.allocate_receipts`).
Переплата уходит в следующие месяцы, недоплата оставляет платёж покрытым
частично (`covered_cents`). `paid_at` в графике остаётся ПРОИЗВОДНОЙ отметкой —
на неё опираются напоминания и дебиторка, и переписывать их незачем; пересчёт
делает `_sync_schedule_state`. Закрытие сделки последним поступлением и
переоткрытие при удалении поступления — В ТОЙ ЖЕ транзакции под `_lock_deal`
(`_set_deal_closed_locked`): отдельным шагом после коммита сбой оставлял
покрытую сделку открытой, а удаление между коммитом и закрытием давало
закрытую сделку без денег. Кнопка «оплачен» — обёртка над поступлением на
плановую сумму.

**Приёмка контейнера (`services/container_receipt.py`).** Приход — обычная
incoming-накладная склада: отдельного вида документа для контейнера нет, иначе
остаток начал бы зависеть от того, каким путём товар приехал. Цены НЕ
спрашиваем при подсчёте (человек считает коробки, а не деньги) — позиции уходят
без цены, закупочную вписывают позже (руководство — блоком «Закупка и
себестоимость» на карточке контейнера, см. «Себестоимость и прибыль»). Поставщик НЕобязателен: МойСклад требовал
контрагента для «Приёмки», локальной накладной он не нужен, и выдумывать
блокировку, которой больше нет, незачем — поле осталось (`container_receipt`),
но приёмку не держит.

**Товар выбирает ЧЕЛОВЕК, а не поиск по названию.** Привязка позиции к карточке
номенклатуры лежит в `container_item_products` (отдельная таблица — колонка в
существующую `container_items` до прода не доехала бы), и `match_items` берёт
`product_id` оттуда. Сопоставление по имени осталось ЗАПАСНЫМ путём для
позиций, заведённых до появления выбора: оно требуется точное, похожие имена не
склеиваем — угадывание означает приход не на ту карточку. Свободный ввод
остаётся законным: в контейнере регулярно едет то, чего в номенклатуре ещё нет,
и требовать карточку до сохранения значит остановить приёмку. Несопоставленное
возвращается списком с `item_id`, чтобы его можно было починить прямо из
карточки, — молча пропущенная позиция это остаток, которого нет.
Карточку заводит `container_receipt.create_product` по кнопке, НЕ автоматически:
автосоздание из приёмки превратило бы каждую опечатку в новый товар справочника.
Дубликат ловим по нормализованному имени, и перепроверяем ВНУТРИ транзакции:
кнопку можно нажать дважды, а UNIQUE на имени нет и быть не должно (тёзки в
каталоге законны).
**Во фронте позицию начинают с ВЫБОРА, а не с ввода** (`openCatalogPicker` —
лист со списком каталога сразу, серверный поиск `/api/products/search` c
`browse` по названию и артикулу, в строке остаток и единица). Раньше товар
вписывали, каталог подсказывал под полем после второй буквы — подсказку не
замечали, и опечатка при приёмке становилась второй карточкой («менеджер может
ошибиться в названии» с площадки). Свободный ввод — отдельной кнопкой «Новый
товар»; `item_add` без `product_id` с именем, которое в каталоге уже есть,
отвечает 409 `needs_choice` + `existing`. Сравнение имён — `normalize_name`
(регистр, пробелы, **ё=е**; SQL отбирает кандидатов шаблоном, точность — в
Python). Непривязанные позиции с фактом решаются ПЕРЕД приходом формой
«Товары без карточки» (`openReceiptReview`): выбор едет полем `resolve`
(`{item_id: {product_id} | {new: true}}`) в `/api/containers/check` и
`/supply`, `resolve_items` привязывает/заводит карточки до накладной. Совпадение
по имени предвыбрано и видно (`catalog_matches` в карточке), без совпадения
выбор обязателен — «новым товаром» опечатка сама не становится.
**Факт сверки и остаток сходятся.** `/api/containers/check` сохраняет количества
и сразу проводит приход; если ПЕРЕоприходование не прошло (товар прежнего
прихода уже отгружен — отмена накладной увела бы остаток в минус), ручка
возвращает прежние количества и отвечает 409 с причиной, а в журнал сверка не
пишется (`audit_checked` — после того, как приход устоял). Раньше ответ был
«ок», карточка показывала новый факт, остаток стоял по старому. Первый приход,
которому нечего проводить, — 200 с `receipt.ok = false`, экран говорит это
отдельным красным сообщением.

**Окно правки приёмки — 24 часа** (`containers.EDIT_WINDOW_HOURS`). После него
карточка закрывается: правки, удаление и добавление позиций отвергает
`_require_open_window` — один сторож на все операции, потому что закрыть
карточку в интерфейсе и принимать правки в ручках значит не закрыть её вовсе.
Расхождением считается только то, что ЗАЯВЛЯЛИ: позиция с `expected_qty == 0`
получает состояние `received`, а не `extra` — контейнер, состав которого не
заводили заранее, это опись прибывшего, а не сверка.

**Рассрочка техники (график).** Взнос — платёж `seq = 0` в
`machine_deal_payments`, а НЕ колонка в `machine_deals`: одно описание вместо
двух, и новая таблица доезжает до прода обычным `CREATE TABLE IF NOT EXISTS`
(инкрементальных миграций в проекте нет — колонка в существующую таблицу просто
не приехала бы). Помечен оплаченным сразу, иначе попал бы в напоминания в день
сделки. Остаток делится поровну, копейки от деления — в ПОСЛЕДНИЙ платёж (сумма
графика обязана сойтись с ценой). Дата прижимается к концу короткого месяца
(`_add_months`): у сделки 31 января иначе нет февральского платежа. Дату
закрытия сделки считает сервис, а не форма. Последний полученный платёж
закрывает сделку и двигает машину в `sold`. Напоминания — в `run_debts_notify`
(отдельным сообщением руководству), условие `due_date <= today` и отметка
`notified_at` ПОСЛЕ отправки: пропущенный прогон не должен съесть напоминание,
а ретрай — прислать дубль.

**Удаление родителя — чисти ВСЕХ детей явно.** На SQLite внешние ключи по
умолчанию выключены, на Postgres энфорсятся: забытая дочерняя таблица не падает
ни в одном тесте и всплывает 500-й на проде (так было с `container_supply`).
Дочерние таблицы перечислены списком (`containers.CHILD_TABLES`), а сторожа —
`test_delete_leaves_no_orphans_anywhere` (контейнеры) и
`test_machine_delete_leaves_no_orphans_anywhere` (техника) — собирают детей ИЗ
СХЕМЫ через `PRAGMA foreign_key_list` и ловят следующую такую таблицу сами.
**Порядок в списке — от листьев к корню**: `container_item_links` ссылается и на
контейнер, и на позицию, поэтому удаляется первой. Порядок проверяет
`test_child_tables_are_ordered_leaves_first`, тоже по схеме, — «нет сирот» на
SQLite проходит при любой перестановке.

**Контейнеры (`services/containers.py`).** Состав описан ДВУМЯ числами:
`expected_qty` (заявлено) и `arrived_qty` (факт). `arrived_qty IS NULL` — «ещё
не считали», а НЕ «приехало ноль»: иначе непроверенный контейнер выглядит как
полностью недостающий, а ноль перестаёт значить недостачу. Расхождения считает
`diff`/`diff_summary`, и сводка отдаётся ещё и в списке — иначе «сверить»
значит открыть каждый контейнер по очереди. Прибытие — CAS по статусу;
прибывший контейнер не удаляется (история приёмки). Позиции всегда ищутся
ВНУТРИ заявленного контейнера — гейт от подстановки чужого id.

**Себестоимость и прибыль (`services/costing.py`, ручки `webapp/costing_api.py`,
фронт `webapp/static/costing.js`).** Всё за выключателем
`app_settings.accounting_enabled` (общий с учётом денег, по умолчанию выкл.;
включает босс кнопкой в «Продажи → Отчёт»). Выключен — хуки ничего не пишут, и
склад/приёмка/отчёты ведут себя как раньше. Что помнить:
- **Метод — FIFO по партиям.** Партия = строка ПРИХОДНОЙ накладной
  (`cost_batches`, одна на накладную+товар), её заводит хук в
  `warehouse.create_invoice_in` — значит любой приход, и контейнер, и ручной.
  Средняя не годится: прибыль «по контейнеру» и курсовая разница «по партии»
  после неё не восстанавливаются. «Средняя себестоимость» на экране — это
  средневзвешенная по НЕпроданным партиям (`current_costs`).
- **Остаток склада = последние партии.** Товар старше учёта партий не имеет и
  уходит ПЕРВЫМ — по ручной `product_prices.cost_price` (`cost_source='manual'`)
  или без себестоимости (`'unknown'`). Остаток партии не хранится: он выводится
  из `sale_costs` по ДЕЙСТВУЮЩИМ накладным, поэтому отмена отгрузки/прихода не
  требует обратного хода — отменённая накладная просто выпадает из выборок.
- **Себестоимость отгрузки замораживается** (`sale_costs`, хук расхода): новая
  закупка прошлую прибыль не двигает. Пересчитывается она только при правке цены
  ТОЙ ЖЕ партии (цену вписали позже / опечатка) — `_recost_sales_in`.
- **Цена контейнера — сутки окна не касаются**: окно стережёт количества, цену
  вписывают, когда пришли бумаги. Шапка (`container_costing`) — валюта и курс
  прибытия «сум за 1 USD» (+ «сум за 1 единицу» для CNY), курс к базовой
  выводится (`rates_from_uzs`). Цены по позициям — `container_item_costs`.
  Сохранение переписывает партии и цены в приходной накладной; переоприходование
  (`after_container_receipt_in`) переносит уже проданное на новые партии.
  Подсказка курса: архив ЦБ → запрос в ЦБ на дату (запоминается в архив) → текущий.
- **Курсы и итоги — Decimal**, курс в БД TEXT (REAL на Postgres = float4).
  Курсовая разница (условная) — только продажи в НЕбазовой валюте из партий с
  курсом прибытия: «по курсу прибытия стоила бы X, по курсу продажи — Y».
- **Права: себестоимость видят admin/boss** (`costing.COST_ROLES`; бухгалтерию
  добавить туда, когда появится). Цена ПРИХОДА = закупочная = себестоимость,
  поэтому `redact_invoice` режет её в `/api/wh/invoices`, `/get`, `/print` и в
  печати из бота. Резать в ответе, не во фронте. Ручная прикидка прибыли в
  `/api/analytics` при включённом учёте не отдаётся (второй расходящийся ответ);
  у отгруженного заказа `/api/orders` берёт прибыль из фиксации.
- Роутер подключён ОДНОЙ строкой в конце `server.py` (ветки параллельные, середина
  файла общая); `gen_role_matrix.py` читает и его. Тесты: `tests/test_costing.py`,
  `tests/test_costing_postgres.py` (TEST_PG_URL), `tests/e2e/test_costing.py`,
  `webapp/static/__tests__/costing.test.js`.

**Канал (`services/channel.py`).** Публикует ЧЕЛОВЕК кнопкой — автопостинга в
канал компании нет. Черновик собирает СЕРВЕР (`/api/channel/draft`), а не фронт:
правило «наружу не уходит ни одна цифра количества» должно жить в одном месте.
Остатки, объёмы поставок и номер контейнера — внутреннее: клиенту не нужны, а
конкуренту рассказывают, сколько вы способны отгрузить. Сторож —
`channel.contains_quantities()` и тест `test_no_builder_ever_emits_quantities`,
который прогоняет все шаблоны разом. Цена — не количество, её печатаем.
Текст поста фронт может править: запрещать это значит заставлять публиковать не
то, что хотели; гарантия относится к сборщику, а не к тому, что человек допишет
руками. Анонс берёт позиции с `arrived_qty > 0` — обещать недоехавшее нельзя, и
само число наружу не идёт. «Залежалось» — ФИЛЬТР каталога в «Складе» (чип
`[data-stale]`, только руководству, как и ручка), а не вкладка: это срез того же
списка товаров. Экран ВНУТРЕННИЙ, поэтому остаток там виден — по нему и решают,
что выносить, — а в пост из отмеченного уходят одни названия. `channel_posts` хранит историю, чтобы один контейнер
не ушёл в канал дважды. Кнопка под постом ведёт в личку менеджера — её
переписку уже считает воронка.
Фото товаров — `services/product_photos.py`, тот же приём, что у техники (файл
в Telegram, у нас идентификаторы). Загружаются ПАЧКОЙ (`pickPhotos`), но по
одному запросу на снимок и ПОСЛЕДОВАТЕЛЬНО: каждый сохраняется отправкой в
Telegram, а он ограничивает частоту сообщений в один чат — веер из двадцати
запросов упёрся бы в отказ на середине. Итог называется честно («загружено 8 ·
не прошли 2»), экран перерисовывается один раз в конце, а на отказ делается одна
повторная попытка — на длинной пачке Telegram притормаживает сам и отпускает
через секунду. Загружаются руками: выгрузка картинок всего
каталога из МС — сотни запросов при падающем бюджете. Канал-хранилище —
`PHOTOS_TG_CHAT_ID` (старое `MACHINE_PHOTOS_TG_CHAT_ID` продолжает работать),
публичный канал — `CHANNEL_ID`.

**Воронка обращений (`services/leads.py` + `handlers/business.py`).** Бот
подключён к личному аккаунту менеджера через Telegram Business и ТОЛЬКО
наблюдает. Два инварианта держатся тестами (`tests/test_leads.py`):
`handlers/business.py` не содержит ни одного вызова отправки (проверка по AST) и
не читает `message.text`/`caption` — в сервис уходят только id, имя и
направление. **Текстов переписки в БД нет и быть не должно**: для метрик хватает
«кто, когда, в какую сторону», а хранение чужих сообщений это ответственность
без выгоды.
Лид — это ЧЕЛОВЕК (`leads.tg_user_id` UNIQUE), а не переписка: иначе «сколько
клиентов обратилось» удвоится, когда один написал двум менеджерам.
Состояния (`replied`, `awaiting_reply`, `silent`, `never_answered`) НЕ хранятся —
выводятся из отметок времени `lead_state()`, поэтому не расходятся с фактами.
Руками ставится только исход (`won`/`lost`): в переписке его не видно. Возврат
клиента (`reengaged`) фиксируется событием В МОМЕНТ сообщения — по агрегатам
паузу задним числом не восстановить. Воронка считает по ПЕРВОМУ обращению в
периоде, иначе активный клиент выглядел бы десятью обращениями и конверсия
падала бы от активности, а не от результата.
**Кто заговорил первым — обязательный разрез** (`first_touch_directions`): лид
заводит ЛЮБОЕ первое сообщение, включая наше собственное после звонка клиента, и
без разделения «обратились» раздувается тем сильнее, чем активнее работают по
телефону. Общий `contacted` при этом НЕ трогаем — по нему сравнивают месяцы,
разделение едет отдельными полями (`by_direction`). Скорость ответа — медиана и
p90 (`reply_speed`), а НЕ среднее, и лиды без ответа в неё не входят: иначе
показатель улучшался бы оттого, что человеку так и не ответили. Состояние
разговора (`STATE_FILTERS`) фильтруется в Python через `lead_state`, а не
условием в SQL — пороги живут в одном месте.
Отклик поста в канале (`channel.post_effect`) — это КОРРЕЛЯЦИЯ, а не атрибуция:
ссылка под постом ведёт прямо в личку менеджера и метки не несёт, поэтому
подписываем «после поста», а не «из поста».

**Звонки (`services/lead_calls.py`).** Позвонившего клиента в `leads` не завести:
`tg_user_id` там `NOT NULL UNIQUE`, а ослабить его на проде нельзя. Поэтому
отдельная таблица, и `lead_id` в ней НЕОБЯЗАТЕЛЕН — звонок от человека без
Telegram это законное самостоятельное состояние, он живёт в списке «кому
перезвонить», а не притворяется перепиской. Привязка (`link_call`) ставится
руками: Telegram номер собеседника не отдаёт, общего поля у звонка с перепиской
нет, и угадывание означало бы чужой звонок в чужой карточке.
**В `funnel.contacted` звонки НЕ идут** — только отдельным полем
`calls_unlinked`: подмешать их значит сломать сравнимость с прошлыми месяцами
в день выката, «конверсия упала» окажется неправдой. Телефон храним дважды: как
ввели (перезвонить) и нормализованным хвостом в 9 цифр (`phone_key` — искать и
позже связывать с `ms_counterparties.phone`). `note` о звонке ЗАКОНЕН — это
запись менеджера о своём разговоре, а не сохранённое сообщение клиента; на
переписку послабление не переносится.
Причина отказа — `lead_lost` (sidecar по образцу `container_supply`) и она
НЕОБЯЗАТЕЛЬНА: кнопку «Не купил» нажимают редко, и обязательное поле привело бы
к тому, что её перестанут нажимать вовсе — потерять сам факт отказа хуже, чем
отказ без причины. Список закрытый: `no_stock` переводится в решение о закупке,
`price` — о цене, остальные нужны, чтобы эти две не собирали на себя всё подряд.
**Телефон клиента из переписки взять НЕЛЬЗЯ** — Telegram не отдаёт боту номер
собеседника ни в каком поле апдейта. Он живёт на карточке контрагента,
и мост «написал → купил» строится привязкой (`leads.agent_ms_id` через
`/api/leads/link`), а контрагента можно завести прямо из карточки клиента
(`services/counterparties.create`). Заводит ЧЕЛОВЕК кнопкой: каждый написавший
— ещё не клиент, автосоздание превратило бы справочник в свалку. Тёзку не
заводим (проверка внутри транзакции): второй одноимённый контрагент разводит
заказы одного клиента по двум карточкам, а склеить их потом нечем. Поиск идёт и
по названию, и по ТЕЛЕФОНУ (цифры без разделителей — номер лежит свободным
текстом). Сальдо взаиморасчётов у контрагента больше НЕТ: «сколько должен»
считает `services.debts`/`receivables` по нашим же заказам, и второй ответ на
тот же вопрос с ним бы расходился.
Требует Telegram Premium у менеджера; `business_connections.can_read = 0` —
типичная причина «клиенты не пишут», поэтому состояние подключений отдаётся
боссу в `/api/leads/list`.

**Деньги: слой дебиторки (`services/receivables.py`).** Заказы в кредит и
рассрочки по технике — два учёта, один вопрос. Всё, что отвечает «где деньги»
(экран «Долги», аналитика «Деньги», отчёт в чат), считается ЗДЕСЬ, а не в
ручках. Правила: остаток по заказу берётся из `services.debts` (не пересчитывай
— это пятый способ посчитать долг); суммы в разных валютах не складываются
молча, блок отдаёт `by_currency` + `base_total` + `partial`, и `partial` обязан
доезжать до экрана; границы просрочки считаются в Python от `local_now()`.
Просроченное в прогноз будущих поступлений не попадает. Дисциплина считается
только по технике: у заказа один `due_date` на весь долг, и приравнивать
частичную оплату к плановому платежу значит выдумать метрику. Покупатель
техники опознаётся по имени (`buyer_key` схлопывает регистр и пробелы) — иного
идентификатора у него нет, пока сделка не привязана к контрагенту МС.

**Долги ПОСТАВЩИКАМ — кредиторка (`services/supplier_debts.py`, схема —
`services/supplier_debts_schema.py`, ручки `/api/suppliers/{debts,payment,terms}`,
фронт — `renderSupplierDebts` в `app.js`, «Деньги → Долги → Поставщикам»).**
Зеркало дебиторки: там должны нам, здесь должны мы. До этого
`supplier_payments` заполнял только разовый перенос истории из МойСклад —
живого пути записи не было вовсе. Что помнить:
- **Долг — это приходная накладная с контрагентом, отдельной сущности нет.**
  Ровно как у клиента (долг = заказ `payment_type='credit'`): сумма долга
  обязана быть той же суммой, по которой товар пришёл на склад, а две записи
  одного числа расходятся на первой же правке цены (её вписывают позже,
  «Закупка и себестоимость»). Приход без суммы в долги не идёт, но и не
  пропадает молча — он отдаётся списком `unpriced` («Приход без суммы»):
  «поставщику ничего не должны» про товар на складе — неправильный ответ.
- **Строки условий по умолчанию НЕТ, и её отсутствие значит «в долг»**
  (`supplier_invoice_terms`): четыреста исторических накладных размечать задним
  числом некому, а долг по ним настоящий. Строка появляется, когда условия
  ЗАДАЛИ: «уже оплачено» (убирает приход из долгов и выплату НЕ выдумывает —
  чем и с какого счёта платили тогда, форма не знает) или срок оплаты. Срок не
  задан — долг стареет со дня прихода, а не «никогда».
- **Выплата — строка `supplier_payments` + сайдкар `supplier_payment_parts`
  (1:1, PK `payment_id`).** В `payments` исходящие деньги не попадают НИКОГДА:
  там деньги ОТ клиентов, и на них считается вся дебиторка. У выплаты один
  способ; «наличные + карта» — это две выплаты, и в ленте они читаются по
  отдельности. `debt_currency`/`debt_amount_cents` — сколько долга погашено (у
  перенесённых из МС сайдкара нет: там валюта платежа и есть валюта погашения).
- **Курс и способ — тот же код, что у оплаты заказа** (`order_payments.
  parse_parts`/`compute_parts`): свой курс не дальше `manual_rate_max_deviation_pct`
  от ЦБ, второй формулы нет. Снимок `fx_rate_to_base` пишется ОБРАТНОЙ
  величиной к `c.rate` (`_fx_to_base`): перепутать — завысить итог в 10⁸ раз.
- **Карта/счёт — тот же справочник `acc_accounts`**, но подпись другая:
  `pay_accounts.source_label` («с карты …», «со счёта …») против
  `destination_label` («на карту …»). Отдельная функция, а не флаг, — чтобы
  выплату нельзя было подписать как поступление; тело записи общее
  (`_account_body`), иначе один счёт в двух лентах читался бы как два разных.
  Выплаты считаются в `pay_accounts.usage_count` и в «последнем выборе».
- **Аванс поставщику — НЕ ошибка** (об этом прямо сказано и в переносе
  истории): общая выплата сверх долга принимается и показывается строкой
  «аванс». А выплата, привязанная к КОНКРЕТНОМУ приходу, больше его остатка —
  опечатка, и отвергается текстом (`code=over`). Общая выплата гасит открытые
  приходы поставщика от старых к новым — это СОГЛАШЕНИЕ (как FIFO у сдач и у
  переноса истории), и валюта обязана совпасть: пересчитать чужую нечем.
- **Замок — строки приходных накладных** (`lock_invoices`, по возрастанию id,
  как `debts.lock_orders`): две выплаты по одной накладной без него обе видят
  прежний остаток и обе проходят проверку «не больше остатка».
- **Права — admin/boss** (`_SUPPLIER_SEE_ROLES`/`_SUPPLIER_RECORD_ROLES` в
  `server.py`; их читает `gen_role_matrix.py`, поэтому кортежи литеральные и
  живут там, а не в сервисе). Сумма прихода — это закупочная цена, то есть
  себестоимость, и экран показывает её прямым текстом: открыть его бухгалтеру
  сегодня значит открыть его и МЕНЕДЖЕРУ (`roles.ROLE_ALSO_ACTS_AS`), то есть
  показать наценку в обход `costing.redact_invoice`. **Открытый вопрос
  владельцу:** аудит просил «бухгалтер вносит выплаты» — это станет возможно,
  когда бухгалтер появится в штате (снимется `roles.PAUSED_ROLES`); тогда его
  добавляют сюда и в `costing.COST_ROLES` одной правкой.
- **Подтверждения у выплаты нет** — это факт, а не заявка (как у поступлений по
  рассрочке). Пуш боссу тоже не шлётся: записывает её сам босс, и рассказывать
  ему о собственном действии незачем. Появится бухгалтер — уведомление идёт
  через `notify_policy.should_notify_now`, и ниже порога обязано доезжать до
  дайджеста, иначе событие исчезнет.
- **Условия можно задать прямо в форме накладной** (`supplier_payment_type` /
  `supplier_due_date` у `/api/wh/invoices/create`, блок «Расчёты с поставщиком»
  у прихода — тот же «В долг / Уже оплачено», что у заказа клиента). Отказ в
  условиях накладную НЕ откатывает: она проведена, остаток на месте —
  ответ несёт `supplier_terms_warning`, экран показывает его тостом.
- Просроченные выплаты — пункт очереди «Сегодня» руководителя
  (`work_queue`, `crit`, адрес `money:suppliers`), рядом с просроченной
  дебиторкой: срок нарушен одинаково с обеих сторон. Адрес прежний, а вкладки
  `suppliers` в разделе НЕТ (см. «Вкладки „Денег“»): `renderMoneyScreen`
  переводит его во второй уровень «Долгов» (`moneyTab='debts'`,
  `debtsSub='suppliers'`) той же строкой, что и прочие внешние ключи вкладок.
- Тесты: `tests/test_supplier_debts.py`, `tests/e2e/test_supplier_debts.py`,
  сценарий `test_stock_day.py::test_container_from_supplier_becomes_a_debt_and_is_paid`,
  инвариант `invariants.supplier_money_is_consistent` (выплата не лежит в
  `payments`, по приходу не выплачено больше его суммы).

**Бухгалтерия, этап 1 (`services/accounting.py`, схема — `services/accounting_schema.py`,
ручки `/api/acc/*` — `webapp/routes_accounting.py`, фронт — `webapp/static/accounting.js`).**
Всё за выключателем `app_settings.accounting_enabled` (по умолчанию выкл.;
включает boss/admin кнопкой внизу «Деньги → Касса», дата старта —
`accounting_start_date`). Выключено — ручки отвечают 409, экраны прежние
(сторож — `test_accounting.py::test_disabled_by_default…` и E2E
`test_accounting_off_keeps_old_screens`). Модель:
- `acc_accounts` — касса/банк/карта, у счёта ОДНА валюта (наличные USD и UZS —
  два счёта). `acc_docs` — документ = одно действие (receipt, expense, transfer,
  exchange, reconcile, opening): статус, отмена с причиной, `request_key`
  (UNIQUE — идемпотентность, документ вставляется ПЕРВЫМ в транзакции).
  `acc_entries` — движения по счетам: сумма в валюте счёта, `rate` (текст-Decimal,
  «единиц валюты за 1 базовую»), `rate_source` base/cbu/manual, `cbu_rate` рядом
  всегда, `amount_base_cents`. `acc_day_closes` — пересчёт кассы (пишется и при нуле).
- **Долг здесь не считается.** «Получил деньги» по заказу пишет обычный `payments`
  в валюте заказа (сумма строк, пересчитанная по курсу документа) той же
  транзакцией, что и строки журнала, под `FOR UPDATE` заказа и с тем же
  `calc_claimable_cents`; дальше — штатное подтверждение босса
  (`confirm_payment` → закрытие заказа). Руководитель, записавший сам,
  подтверждается сразу. Рассрочка — `machines._insert_receipt_locked` в той же
  транзакции. Переплата сверх остатка (допуск 1 единица валюты на округление) — отказ.
- **Остаток = приходы − расходы по ДЕЙСТВУЮЩИМ документам** (`EFFECTIVE_SQL`):
  документ без основания (платёж отклонён старой кнопкой, поступление по
  рассрочке удалено) выпадает из остатков сам — хуков в чужих модулях нет.
  Удаления нет: отмена (`void_doc`) снимает основание (reject платежа, сторно
  подтверждённого платежа с переоткрытием заказа — только boss; delete_receipt),
  потом гасит документ. Менеджер отменяет только своё и только в день записи.
- Обмен: обе стороны равны в базовой валюте, курс выводится из фактических сумм.
- Роли — константы `ROLES_RECORD/MANAGE/SEE_ALL` в сервисе (менеджер видит в
  журнале только свои документы). `gen_role_matrix.py` эти ручки не видит (он
  парсит только `server.py`) — права смотреть в сервисе.
- UI: вкладка «Касса» при включённой бухгалтерии = «Сейчас · Операции · Ещё»
  (новой вкладки нет — у руководителя их уже 4); «Ещё» — старые формы (возвраты,
  сдачи). В «Долгах» «Отметить» заменяется на «Получил деньги». Точки входа в
  app.js — только через `typeof accX === 'function'`. Пикер поверх формы рисует
  список в СВОЕЙ шторке (`openListPicker` → `sheet.sheet`). Себестоимость/прибыль
  здесь не считаются.

**Rich Message (Bot API 10.1–10.3, aiogram 3.31).** Бот умеет слать в чат статьи с
заголовками, списками и ТАБЛИЦАМИ (`services/money_report.py`). Это снимает
причину, по которой T3.3 уводил всю глубину в WebApp, но не отменяет само
правило: в чат уходит СВОДКА, действия остаются в WebApp. **Фолбэк
обязателен** — при любой ошибке `send_rich_message` тот же отчёт уходит текстом
через `tg_send_message`; отчёт, который не дошёл, хуже некрасивого. Текстовая
версия несёт те же разделы, а не огрызок, и экранирует имена (`esc`): сообщение
идёт с parse_mode=HTML, и контрагент «ООО <Строй>» иначе рушит разметку целиком.
Из 10.3 в отчёте: `is_compact` у таблицы сроков, полный список просроченных
должников в `InputRichBlockExpandableBlockQuotation` (в фолбэке —
`<blockquote expandable>`, строки общие — `_overdue_lines`) и кнопка в WebApp
`InputRichBlockButtons` (в фолбэке — web_app-кнопка в `reply_markup`). Правило
для каждого нового элемента статьи: у него есть текстовый двойник в фолбэке;
web_app-кнопка — только при https `WEBAPP_URL` (иначе Bot API отвергает всё
сообщение), и это одно условие на обе версии (`money_report._webapp_url`). Текст
в Rich-блоках — не HTML, `esc` там не нужен. Блок-документ (`InputRichBlockDocument`)
НЕ используем: накладную и расписку пересылают клиенту, а статья пересылается
статьёй, не файлом, — PDF остаётся `send_document` с кнопкой «Распечатать».

**Кнопки карточек (Bot API 10.3) — `utils/keyboards.py` + `handlers/_ui.py`.**
- **Исход — неактивной кнопкой, а не пропавшей клавиатурой.** После решения
  кнопки решения заменяются `disabled_button` с исходом «✅ Одобрено · Фаридун
  14:05» (`outcome_label`: имя, не ФИО, + время), пометка ТЕКСТОМ в сообщении
  остаётся (история; клиент без 10.3 видит хотя бы её). Заменяй через
  `settle_markup(message.reply_markup, callbacks, label, tail=webapp_keyboard(…))`:
  он гасит только строки с колбэками ЭТОЙ сущности — в пачке платежей из WebApp
  по строке на платёж, в `/frozen` по кнопке на заказ, и решение по одному не
  должно убивать соседей; `tail` («что дальше» — WebApp) встаёт, когда живых
  решений не осталось. Колбэков у неактивной кнопки нет — Telegram не шлёт
  ничего, `test_no_dangling_callback_buttons_in_bot_code` её не видит.
- **Устаревшая карточка обязана гаситься, а не только отвечать алертом.**
  id сообщений карточек мы не храним, поэтому решённое в WebApp или вторым
  руководителем остаётся в чате с живыми кнопками. Хендлер на «уже обработано»
  перечитывает сущность и, если она уже не pending, зовёт `settle_card` с
  исходом из статуса («✅ Заявка уже одобрена») — `_settle_stale_request/
  _payment/_deposit/_return`. Сущность ещё ждёт (отказ по лимиту, «сначала
  отметьте приёмку») — кнопки НЕ трогаем. Вход в ввод причины по устаревшей
  карточке не начинается.
- **Недоступный шаг — неактивной кнопкой с причиной**, только если он
  разблокируется не на этой копии карточки: «🚚 Отгрузка — после ввода оплаты»
  (одобрение «оплаты сразу» менеджеру, отказ `/ship`), «💵 Принять — через сдачу
  в кассу» (наличный платёж). «Подтвердить возврат» до приёмки товара
  НЕактивной не делаем: карточку получают и кладовщик, и руководитель, приёмку
  отмечают на одной копии — у второй кнопка осталась бы мёртвой навсегда.
- **Вопрос «напишите одним сообщением» — `prompt_keyboard(...)`**
  (`InlineKeyboardMarkup(force_reply=True)`): поле ответа открывается сразу, а
  кнопка отмены остаётся. Карточка на время ввода — `drop_keyboard(call,
  status="✍️ Ждём причину…")`; отмена ввода (`req_draft_abort`, `dep_no_abort`)
  возвращает карточке кнопки, если сущность ещё ждёт; после причины — погасить
  и вопрос (`set_message_markup(..., None)`), и карточку (`finish_message(...,
  outcome=…)`). Кнопка отмены со старого вопроса проверяет FSM-состояние и
  отвечает «Уже неактуально», а не «отменено» по уже проведённой операции.
- **Ephemeral-сообщения (10.2/10.3) не используем**: они только для групп, а бот
  работает в личке (Business-подключение — только наблюдение). Появится
  групповой чат — `ephemeral_message_parameters`, НЕ `receiver_user_id`/
  `callback_query_id` (в 10.3 устарели).

**Аналитика менеджеров:** только из ЛОКАЛЬНЫХ `orders` (`get_manager_performance`, GROUP BY `user_id`) — в demand'ах МС нет надёжной привязки к менеджеру (`telegram_full_name` ставится лишь когда demand создал бот). Сурфейсится в webapp company-аналитике (`top_managers`).

**Какая версия работает — `services/version.py`, один источник на оба процесса.**
`bot` и `webapp` поднимаются из ОДНОГО образа, но это разные контейнеры, и
пересоздать можно один из двух — тогда половина правок работает, а половина
нет, и выглядит это как новый баг. Сверить их можно, только пока оба считают
SHA одинаково, поэтому `webapp/server.py` больше не считает его у себя.
- Источник — `GIT_COMMIT_SHA`/`GIT_COMMIT_MESSAGE`, проставленные НА СБОРКЕ
  (`Dockerfile`: `ARG` → `ENV`), а НЕ `.git`: `.dockerignore` историю в образ
  не кладёт, и `git rev-parse` внутри контейнера всегда пуст. Подставляет их
  **`scripts/deploy.sh`** — руками их забывают, и версия молча скатывается к
  таймстампу старта (кэш статики при этом слетает у всех на каждом рестарте).
  `RAILWAY_*` остались вторым шагом: проект жил там раньше. `git rev-parse` —
  третий, для запуска из исходников; таймстамп старта — последний (он не
  отвечает «какой коммит», но отвечает «когда перезапустили»).
- **Заголовок коммита важнее SHA**: восемь шестнадцатеричных знаков человек с
  GitHub по памяти не сверит, а «Пикеры вместо нативных меню…» сверяется сразу.
- Наружу версия выходит тремя путями: `/healthz` (+ uptime и mode, без
  авторизации — закрытый healthcheck не годится мониторингу), поле `version` в
  `/api/me` → мелкая строка внизу «Сегодня» у руководства, и `/version` в боте.
- **`/version` существует ради ОДНОЙ строки** — «сервисы на разных коммитах».
  Свою версию бот знает и так; ценность в том, что он спрашивает WebApp
  `/healthz` и сравнивает, а расхождение выносит выводом с эмодзи, а не парой
  SHA, которые надо сличать глазами. WebApp не ответил — это тоже результат
  («сервис лежит»), печатается причина и своя версия. Заголовок коммита едет в
  `parse_mode="HTML"` → обязателен `esc()`.

**Backup:**
- `tasks/run_backup`: если `pg_dump` упал (нет бинаря — `FileNotFoundError`, ИЛИ `server version mismatch` — `RuntimeError`: бинарь старее managed-Postgres) → fallback на version-independent pure-Python COPY-dump (`_pg_dump_pure_python` через libpq). Лови ОБА исключения.
- `tasks/run_maintenance`: janitor чистит дедуп отгрузок, аудит старше ретеншена (`prune_audit_log`, `audit_log_retention_months`) и soft-deleted. Внешний архив аудита (Google Drive) убран.

**Time:** `utils.helpers.utc_now()` вместо deprecated `datetime.utcnow()`. `utils.helpers.local_now()` для сравнений с `created_at` (пишется в local TZ через `now_str()`).
- В SQL **не** сравнивай `confirmed_at`/`created_at` (local TZ string) с `datetime('now',...)` SQLite (UTC) или `NOW()` Postgres — лекс-сравнение в разных TZ молча всегда False (silent bug). Вычисляй порог в Python через `datetime.now() - timedelta(...)` и передавай параметром. Пример — `services/database.reset_stale_in_progress_payments`.

**Idempotency:** `/api/orders/{confirm_payment,mark_paid,payment,reject_payment}` принимают `idempotency_key` через `_idem_get/_idem_set`. ВАЖНО: всегда вызывай `_idem_set` ПОСЛЕ успеха (был баг — `reject_payment` делал только `_idem_get` → ретрай слал дубль-уведомление). Применяй паттерн для новых write-endpoint'ов.
Денежные create-ручки (разбивка `payment`/`mark_paid`, сдача, возврат) — `_Idem(..., atomic=True)`:
операция пишет результат в ключ СВОЕЙ транзакцией (`database.idem_store_in`,
ей передаётся `idem.key`), поэтому ключ без результата старше
`IDEM_RECLAIM_AFTER_S` значит «не закоммитилось» и переиспользуется. У
неатомарных ручек пустой ключ может скрывать проведённую операцию — там
только 409. Проверки между `claim()` и операцией — внутри
`async with idem.released_on_reject():`, иначе 4xx держит ключ сутки.

**Logging:**
- НЕ дёргай root logger (`logging.warning(...)`/`logging.info(...)`) на module-import time. Первый же вызов авто-триггерит `basicConfig(level=WARNING)` с дефолт-форматтером, и любой последующий `logging.basicConfig(level=INFO, ...)` в bot.py/tasks/run_*.py становится no-op → ВСЕ INFO глушатся на проде. Используй `logger = logging.getLogger(__name__)` — propagation идёт через `lastResort`, root остаётся чист.
- В cron-CLI (`tasks/run_*.py`) ставь `logging.basicConfig(level=INFO, format=...)` ДО любого импорта, который потенциально логирует на module-уровне. Сейчас все cron-CLI и `bot.py` это делают корректно.

**Cron-CLI стабильность:**
- Перед основной логикой вызывай идемпотентный reaper для своих долгоживущих in-flight состояний. Пример — `services.database.reset_stale_in_progress_payments(30)` в начале `tasks/run_ms_sync_retry`: сбрасывает orphan'ов 'in_progress' (claim был, но процесс убили до set_failed). Без него стуки залипают навсегда, потому что `claim_payment_for_ms_sync` отвергает уже-'in_progress'.
- В `tasks/run_ms_sync_retry`: pending-fetch ДО любого МС-вызова, `return 0` на пустой очереди ДО `init_demand_context()` — иначе 96 cron-тиков/день делают ~200-400 МС API calls впустую.
- `init_demand_context()` сам по себе НЕ raises (helpers `_pick_first`/`_ensure_custom_attribute` глотают exception); инспектируй возвращаемый dict (`ready/org/store/attribute_name/attribute_uid`), а не оборачивай в `try/except` (dead code).

- **Обращение к человеку — только «вы»** (без заглавной): «Выберите товар»,

- **Кнопка называет действие с предметом**, а не глагол вообще: «Оформить

- **Одно слово — один регистр.** Термин внутри фразы — со строчной («оформите

- **Английского на экране нет.** `approved`, `pending`, `void` — коды; у них

- **Согласование по роду** — по слову, к которому относится: заказ *отгружен*,
  заявка *отклонена*, сдача *подтверждена*. Смешивать средний род («Отгружено»)

- **Числа в документах и на экране — по-русски**: `1 092,00`, а не `1,092.00`.

- Ключи экранов, вкладок, `data-*`, поля API, `code` в ошибках и коды аудита —

## Тесты (конвенция)

Мокай ГРАНИЦУ с внешним миром, а не свой код. Урок: баг в `tg_send_message` пережил CI, потому что тесты мокали саму `tg_send_message`. Для исходящих HTTP — `aioresponses` (мок транспорта, реально исполняется сборка URL/payload). БД — настоящая (`isolated_db`), не мок.
У best-effort функций (глотают исключения) проверяй ВОЗВРАТ, а не только «запрос ушёл»: на aiohttp 3.14 aioresponses 0.7.9 не собирал ответ (TypeError), `tg_send_message` это глотал, и тест URL оставался зелёным. Шим для aioresponses — в `tests/conftest.py`, сам отключается на исправленном релизе.

Если добавляешь module-level `asyncio.Semaphore`/`Lock` — добавь регресс-тест с 2× `asyncio.run` и contention >cap (см. `tests/test_analytics_parallel.py::test_positions_semaphore_survives_multiple_asyncio_run_with_contention`). Без waiter'а в очереди loop-binding не воспроизводится и landmine ждёт первого «толстого» теста.

**E2E (`tests/e2e/`, маркер `e2e`, отдельный job в CI).** Настоящий Chromium
(Playwright, sync API) грузит WebApp с живого uvicorn в том же процессе, fetch
настоящие, БД — `isolated_db`. Закрывает дыру между API-тестами (фронта нет) и
jsdom-смоуком (сервера нет): первый же прогон нашёл, что диалог количества
сравнивал `currentScreen` с несуществующим `'orders'` и позиция никогда не
попадала в редактор — ни один слой ниже этого не видел. Мокается только граница:
подпись initData (`verify_init_data` → initData = user_id), SDK Telegram
(`page.route` подменяет `telegram-web-app.js` заглушкой с настоящей по форме
`MainButton`; жмётся `window.__tgMainClick()`), исходящие в Telegram. Роли —
настоящие, из `user_roles`. `asyncio.run` из теста нельзя: sync-API Playwright
держит в потоке работающий loop, поэтому корутины гоняет `e2e.run()` в отдельном
потоке. Без Playwright/Chromium пакет пропускается; `E2E_REQUIRED=1` (CI)
превращает пропуск в падение. Бинарь без установки — `PW_CHROMIUM_PATH`.
Найденный E2E баг закрепляй ещё и быстрым jsdom-регрессом в
`app-load.smoke.test.js`: он идёт в frontend-job за секунду.
Файлы — по разделам: `test_webapp_flows.py` (навигация и продажа),
`test_sales_money.py`, `test_stock.py`, `test_clients_auth.py`. Сценарий
начинается ПОСЛЕ того шага, который уже покрыт: продажу заводит `seed_order`
через сервисы, а не через редактор — иначе каждый тест платит полминуты
браузера за чужую проверку. Что ловило вторую волну: (1) сервер отвечает
`needs_override` кодом 200, и `api()` это не исключение — успех проверяй по
телу; (2) у роли с одной вкладкой раздел рисуется БЕЗ переключателя
(`sectionNavHtml` при `< 2`), `tab()` там ждать нечего; (3) `showConfirm`
кладёт свой текст в `window.__tgAlerts` с префиксом `confirm:` — ждать
«отгружен» значит поймать вопрос «Отметить отгруженным?», жди эмодзи ответа;
(4) сдача (`create_cash_deposit`) распределяется по наличным строкам разбивки
на руках, остаток — по `shipped` долгам; одобрение оставляет заказ `approved` —
«отгружен» ставит кладовщик отдельно, а «оплату сразу» — только после разбивки.

**Сценарии (`tests/scenarios/`, только `TEST_PG_URL`).** Цепочки шагов разных
ролей через HTTP-ручки на живом Postgres: товар → приход, контейнер → остаток,
заказ → одобрение → отгрузка → оплата → сдача → долги, отмена и возврат,
техника → рассрочка, границы ролей. Сервер — `tests/liveserver.py`, клиент —
httpx. Правила: (1) шаги — функции `tests/scenarios/flows.py`, сценарий payload
сам не собирает: поменялся поток — правится одна функция; (2) состояние БД —
синхронным слоем (`w.rows`), НЕ `run_async`: он с другого loop'а рвёт
asyncpg-пул сервера посреди фоновых задач; (3) после сценария фикстура `world`
проверяет инварианты (`invariants.py`, считают НЕЗАВИСИМО от `services.debts`):
остаток ≥ 0 и = приходы − расходы по действующим накладным, заявлено по заказу
≤ сумма − возвраты, «оплачен» только при нулевом остатке, по отменённому
заказу нет живых платежей, отгруженное списано накладной, «Долги» = расчёт по
строкам, разбивка оплаты сходится (строка = платёж того же заказа в его валюте,
сдача берёт наличную строку целиком в своей валюте и не двумя живыми сдачами,
подтверждённая сдача — подтверждённые платежи строк, наличные подтверждены
только сдачей, распределено сдачей ≤ сдано), аудит пишется, 5xx и ERROR в логах
нет; оплата — `flows.record_payment` (разбивка), `flows.ship_order(payments=)`
вносит её от автора заказа перед отгрузкой; (4) известный баг — тест на
ПРАВИЛЬНОЕ поведение с `xfail(strict=True, reason=…)`: починили — xfail
«проходит» и валит прогон, маркер снимается вместе с фиксом. Два браузерных
дня с теми же инвариантами — `tests/e2e/test_journeys.py`.

**Perf-слой (`tests/perf/`, маркер `perf`, отдельный job в CI).** Четыре
инструмента, у каждого своя задача:
- **N+1 — по масштабированию, а не по абсолютному числу** (`test_query_counts.py`).
  Фикстура `query_counter` считает SQL в ОБОИХ слоях (`_TimedCursor.execute` и
  `aiosqlite.Connection.execute`); ручка меряется на 6 и на 60 строках, и
  разница обязана уложиться в `SLACK`. Абсолютное число не инвариант (рефакторинг
  законно меняет его на ±2), линейный рост — ровно тот баг. Первый прогон нашёл
  N+1 в списке заявок босса: кредит-контекст по каждой заявке (6 запросов на
  строку). Теперь долги и лимиты берутся батчем: `get_agents_current_debt` /
  `get_credit_limits` / `orders_credit_context`; одиночный
  `get_agent_current_debt` — обёртка над батчем, формула долга одна.
- **Размер ответа** (`test_payload_size.py`): байт на строку — свойство формата,
  порог жёсткий; время — щедрое (секунды), ловим порядок, не миллисекунды.
- **Нагрузка на живой сервер** (`test_load.py`, каркас `tests/liveserver.py`
  общий с E2E, сверху httpx): проверяется КОРРЕКТНОСТЬ под параллельностью —
  двадцать заявок разом, одновременные «Одобрить» по одной заявке, ретрай с тем
  же ключом, заявок больше, чем товара. Последовательно эти баги не видны.
- **Бенчмарки** (`test_benchmarks.py`, pytest-benchmark): порогов по времени
  НЕТ намеренно — CI-раннер шумит, и порог валил бы сборку из-за соседа по
  машине. Цифры идут в лог; регрессию сложности ловят тесты масштабирования
  («10× данных — не дольше 25×»).
Массовый сид — `tests/perf/_seed.py`, прямыми INSERT'ами: сервисные функции
делают по 3–5 запросов на строку, и 5 000 товаров через них — минута на тест.
**SQLite под параллельностью.** Нагрузочные тесты показали три вещи, которых
нет на Postgres, и все три закрыты в SQLite-ветке: (1) `adb_core.transaction()`
открывается `BEGIN IMMEDIATE` — отложенная транзакция «прочитал остаток → списал»
давала двум читателям пройти проверку одновременно (остаток уходил в минус; на
Postgres от этого держит `FOR UPDATE`) и отвечала «database is locked» СРАЗУ
при апгрейде SHARED→RESERVED, не дожидаясь timeout; (2) busy-timeout 30 с вместо
5 в обоих слоях; (3) `PRAGMA journal_mode=WAL` при `init_db` — читатели не ждут
писателя. **НЕ ставь `BEGIN IMMEDIATE` в синхронный `get_conn`**: async-транзакция
зовёт sync-функции через `to_thread` (`get_setting`, `get_role`), и sync-коннект
ждал бы собственную транзакцию — это уже пробовали, получили таймауты на всём.

**Выбор из справочника — `openListPicker`, а НЕ нативный `<select>`.** В
Telegram-WebView он разворачивается системным списком во весь экран: без
поиска, без подстрочника, с обрезанными именами — на сотне контрагентов это
пролистывание вслепую («уродское меню» с площадки). Пикер — лист с поиском:
`items: [{id, name, sub}]`, фильтрация локальная (справочник уже в памяти),
клик по строке только помечает её, выбор уходит в `onPick` по «Выбрать».
Так выбираются контрагент и товар в форме накладной; новые длинные справочники
делай так же. **Нативных `<select>` во фронте не осталось вовсе**: короткий
выбор из нескольких вариантов рисует сегмент (`openMachineSheet`, `type:
'select'`) — он открывает тот же системный диалог во весь экран даже ради двух
пунктов. У сегмента, в отличие от `<select>`, «ничего не выбрано» — законное
состояние разметки, поэтому пустое значение поля встаёт на ПЕРВЫЙ вариант:
иначе обязательный выбор отвечает «Заполните: …», хотя варианты лежат перед
человеком (так сломалась форма расписки). Значение держит скрытое поле — общий
`values()` не обрастает веткой сбора.

**Контрагента заводят из ПИКЕРА, кнопкой под списком** (`addLabel`/`onAdd` →
`openCounterpartyForm` → `/api/wh/counterparties/create`). Справочник
пополнялся только из карточки клиента в «Воронке», а накладную выписывают на
складе: приезжал новый покупатель — выбрать его в форме было не из чего, и
отгрузка вставала («не могу добавить, работа останавливается» с площадки).
Кнопка стоит под списком, а не отдельным экраном: нового ищут ровно там, где
не находят старого, а уводить человека из накладной значит потерять набранное.
Набранное в поиске уезжает в название. Сервис тот же (`counterparties.create`):
тёзка не заводится, повторное нажатие возвращает уже заведённого (`existed`).
Заведённый дописывается в `whCounterparties` — справочник тянется один раз на
сессию экрана, и без этого следующий выбор его не покажет.

**Подсказка прокрутки (`.scroll-hint`).** Ряд вкладок или чипов, который не
влез, обрывается ровно по краю экрана, и обрезанная подпись читается как «так
и задумано». Обёртка `.scroll-hint` затеняет край, сторона зависит от
фактической позиции (`data-more`, ставит `refreshScrollHints`). Затенение
рисует ОБЁРТКА, а не сам скроллер: псевдоэлемент внутри прокручиваемого блока
уезжает вместе с содержимым. Наблюдатель висит на `document.body`, а НЕ на
`#content`: `showScreen` подменяет узел `#content` свежим, и наблюдатель на
нём после первого же перехода сидел бы на отсоединённом узле.

и второе правило переписывало у первого восемь свойств. Файл при этом валиден,

там переопределяется одно свойство; сторож в `design-system.test.js` считает

уровне (тело `@media`/`@supports` он не смотрит — там переопределение и есть
задача блока).

**Расписка — один бланк юриста, три вида.** Исходник —
`templates/legal/src/raspiska_ru_uz_source.docx` (финальный бланк: РАСПИСКА +

«… сум», и долларовая сумма под этим словом занижала бы долг в тысячи раз.

Число платежей 1 — разовый график из одной строки, 2+ — рассрочка.

**Шторка «Меню».** В нижней панели —
до ПЯТИ разделов (`NAV_BAR_MAX` = 5; было четыре, пятый слот отдали
«Клиентам» — решение владельца, список покупателей открывается одним
касанием), шестой слот — «Меню» (`data-action="menu"`,
не `data-screen`): шторка справа деревом «раздел → вкладки» под роль
(`navBarLayout`/`navDrawerHtml` в `helpers.js`, `openNavDrawer`/`closeNavDrawer`
в `app.js`). Ряд `.seg` внутри раздела остаётся. Роль, у которой шторка повторила
бы панель (нет раздела сверх четырёх и нет раздела с ≥2 вкладками), «Меню» не
получает. Раздел из шторки подсвечивает «Меню»; текущий раздел для тестов —
`#bottom-nav[data-current]` (e2e `go()` сам ходит через шторку). Переход из
шторки — `showScreen(section, { tab })`: вкладка ставится ПОСЛЕ алиаса
`LEGACY_SCREENS`, иначе вкладка алиаса её затирает. Список разделов роли в e2e —
`nav_screens(page)` (панель + шторка), текущий раздел — `current_screen(page)`;
`.nav-item.active` для раздела из шторки пуст.
Шторка берёт «Назад» Telegram и при закрытии возвращает «Назад» экрана под ней.
**Руководитель: «смотреть, решать, контролировать» (решение владельца).** У
admin/boss порядок разделов свой (`BOSS_NAV_ORDER`): панель «Сегодня · Решения ·
Деньги · Продажи · Клиенты · Меню», склад, обращения и «Настройки» — в шторке. Вкладки
под роль — одна чистая функция `roleSectionTabs(section, role, {work})` в
`helpers.js` (app.js `sectionTabsFor` — обёртка). Работа менеджера (накладные,
«Отгрузить»/«Внести оплату», «Касса», «Документы», «Лиды», «Канал», моточасы,
правка/статусы/продажа техники, приёмка контейнера, «Товар получен», отметки
рассрочки, фото) у руководства — за выключателем **«Рабочие действия»** в
«Меню» и «Настройках»: `workActionsVisible()` (у остальных ролей всегда true —
их интерфейс не менялся). Это личная настройка ВИДА, а не права: таблица
`user_prefs` (`services/user_prefs.py`), `/api/me → prefs`, `/api/prefs/set`
(admin/boss, аудит `pref_set`); ручки её не читают. Удаление — контроль:
`deleteActionsVisible()` — руководству всегда, менеджеру пока
`delete_requires_boss` (из `/api/me`, нет поля — выкл.; выключатель — в
«Настройках») не включена; кнопка удаления машины/контейнера смотрит
`can_delete` карточки, пока его нет — `can_manage`. Решение по чужой заявке
(сделка по технике: одобрить/отклонить/на доработку) — тоже не работа, видно
всегда. **«Решения»** (`renderDecisionsScreen`) — все подтверждения
руководства одним экраном с общим бейджем на панели (`setDecisionsBadge`;

Подтвердить» (`depositCardsHtml`/`returnCardsHtml`/`paymentCardsHtml`/

адреса `money:confirm` и `requests` у руководства ведёт в «Решения»
`resolveScreen`, у остальных `decisions` — в «Подтвердить». **Deep link:**
`?startapp=decisions` (web_app-кнопка — `utils.keyboards.webapp_screen_url` /

**Поколение экрана (`screenGen`/`bumpScreenGen`).** Рендер асинхронный, и
человек уходит раньше, чем пришёл ответ: «Сегодня» ждала `/api/home`, он нажал
«Деньги» — и главная дописалась поверх «Денег». `showScreen` подменяет узел
`#content` свежим (рендер со ссылкой на старый пишет в отсоединённый элемент) и
поднимает поколение; `setSectionTab` тоже поднимает. Рендер, который ищет
`#content` ЗАНОВО после `await` (`renderOrders`→`renderOrdersMain`,
`renderSalesReport`→`renderAnalyticsContent`, `renderStock`→`renderStockContent`),
обязан запомнить `screenGen()` до ожидания и молча выйти, если оно сменилось.
Новый экран с таким же паттерном — тот же предохранитель. Сторожа —
`test_navigating_away_during_load_does_not_bring_old_screen_back` и
`test_switching_tab_during_orders_load_keeps_report` (E2E, задержка ручки
через monkeypatch `services.async_db`).

**«Сегодня» — очередь дел, а не витрина** (`services/work_queue.py` →
`/api/today`). Состав и ПОРЯДОК считает сервер: порядок это и есть ответ на «с
чего начать», а в шаблоне он разъедется с ролями при первой правке.
Просроченные деньги (`crit`) выше ждущего решения (`warn`), оно выше «клиент
молчит» (`info`); внутри одной срочности — по величине счётчика. Каждый пункт
несёт `screen` с вкладкой (`money:debts`) — счётчик без адреса заставляет
искать руками то, о чём сам же сообщил. Сбой одного счётчика гасится в лог:
экран с четырьмя пунктами из пяти полезнее, чем ошибка вместо всех пяти.
Ручка отвечает ВСЕМ рабочим ролям — за счёт этого «Сегодня» есть и у
кладовщика с бухгалтером, которым `/api/home` не отвечает (у них экран
состоит из одной очереди).
**Стекло (S7) — только на неподвижном.** `backdrop-filter` стоит на нижней
панели, переключателе вкладок и утилите `.u-glass`; на строках списка его нет и
быть не должно — размытие полусотни строк роняет прокрутку в WebView, а текст на
полупрозрачном фоне теряет контраст. Тинт (`--glass-bg`/`--glass-edge`/
`--glass-spec`) включается ТОЛЬКО внутри `@supports (backdrop-filter)`: без
размытия полупрозрачная панель нечитаема, поэтому базовое правило красится
плотным `--bg-card`. Под стеклом лежит собственное поле (точечная сетка + две
диагональные полосы): в Telegram фон задаёт тема пользователя и он часто
плоский — размывать было бы нечего. Рисует его ФИКСИРОВАННЫЙ ПСЕВДОЭЛЕМЕНТ
`body::before`, а НЕ `background-attachment: fixed`: последний уводит
Chromium/WebView на медленный путь композитинга, и sticky-шапка на прокрутке
начинает рисоваться со смещением — заголовок уезжает под шапку Telegram. Поле выводится из `--accent` через
`color-mix`, и он ОБЯЗАН быть за `@supports (color: color-mix(…))`: невалидное
значение делает custom property guaranteed-invalid, и `background` со ссылкой на
неё отваливается целиком — страница осталась бы вообще без фона. Украшения
снимает `@media (prefers-contrast: more)`.
Состояние строки списка показывает полоса слева (`.c-row[data-status]::before`),
а не только цвет текста: на площадке при ярком солнце цвет теряется первым.
Инварианты держит `webapp/static/__tests__/design-system.test.js`:
забытый цвет статуса, отсутствие тёмного варианта, таргет мельче 44px,
размытие не на том элементе и color-mix без фолбэка валят CI.
Статус, объявленный только у конкретного класса (как `in_stock` у
`.stock-badge`), в ОБЩЕЙ матрице не появляется — для него нужна отдельная
строка, иначе элемент останется бесцветным при формально «объявленном» статусе.
Права по ролям для ручного QA: `python scripts/gen_role_matrix.py` → `UI_QA_ROLES.md`.

**Сеть фронта — один слой (`webapp/static/net.js`, подключён между helpers.js и
app.js).** `api()`/`apiResult()` — тонкие обёртки над `createNet().request`:
срок 20 с (AbortController + гонка со сроком; PDF/печать/выгрузка/фото
передают `timeoutMs`), обрыв и срок — «Нет связи — проверьте интернет и
повторите» (`errorBoxHtml` рисует его как «Нет подключения»), 401 — экран
«Сессия истекла» поверх всего (`showSessionExpired`, кнопка `tg.close`).
Прямых `fetch` в app.js нет (сторож — `audit-front.test.js`); картинки —
`_net().request(..., { raw: true })`. **Ошибка загрузки — не пустой список**:
не глуши `api(...).catch(() => [])` там, где пустота что-то значит («нет
записей на подтверждении»), — рисуй `errorBoxHtml` с «Повторить». **Роли
кнопок и запросов** — `canCall(path, role)` по таблице `API_ROLES` (зеркало
`allowed_roles` сервера; `net.test.js` сверяет её с server.py, поменял права
ручки — поправь строку таблицы). **Черновики форм** (накладная, формы
«Кассы») — `formDrafts()` → localStorage под id пользователя, с try/catch и
сроком 3 дня: подпись Telegram живёт час, и набранное не должно пропадать на
401. Суммы из полей ввода — `parseAmount` («1 500», «12,5»; мусор — NaN),
поле суммы — `type="text" inputmode="decimal"`: `type=number` отдаёт пустую
строку на «1 500». `formatMoney` показывает копейки, когда они есть (UZS —
всегда целым). `/api/orders` с `limit` отдаёт страницу (`statuses`,
`date_from`/`date_to` применяются ДО нарезки, всё в SQL — `get_orders_page`;
`pending_count` — по всем заказам роли); без `limit` — прежний ответ целиком.
