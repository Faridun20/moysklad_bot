# DEPLOY — выкат бота на Railway с нуля

Пошаговый порядок для чистого проекта. Топология и «почему так» — в
[ARCHITECTURE.md §2](ARCHITECTURE.md#2-топология-railway); здесь — что нажимать
и в каком порядке, плюс места, где легко обжечься.

Итог выката: **два постоянных сервиса** (бот + WebApp), **Postgres**, **Redis**
и **восемь cron-задач**.

---

## 0. Подготовить до захода в Railway

| Что | Где взять |
|---|---|
| `TELEGRAM_TOKEN` | @BotFather → `/newbot` (или `/token` у существующего) |
| `ADMIN_IDS`, `BOSS_IDS` | Telegram user_id (перешлите своё сообщение в @userinfobot), CSV через запятую |
| Приватный канал для бэкапов | Создать канал → добавить бота администратором с правом Post Messages → узнать `chat_id` (переслать сообщение из канала в @userinfobot) |
| Секрет для Telegram-вебхука | `openssl rand -hex 24` — понадобится только в однопроцессной топологии (`TG_WEBHOOK_SECRET`) |

**Переносите данные из МойСклад?** Тогда нужен ещё `MS_TOKEN` (профиль
пользователя → «Токен доступа») — но только на время прогона
`scripts/migrate_from_moysklad.py`. Приложение его не читает: учёт локальный.

## 1. Проект, база, Redis

1. Railway → **New Project** → подключить репозиторий через GitHub.
2. **+ New → Database → PostgreSQL**.
3. **+ New → Database → Redis**.

Redis формально опционален, но без него FSM aiogram живёт в памяти процесса:
недописанный черновик заказа, введённая причина отклонения и загрузка фото
техники теряются при каждом редеплое и рестарте. На проде — ставить.

Volume приложению не нужен: файловая система эфемерна, и код на это
рассчитывает (бэкап стримится в Telegram, фото техники хранятся как `file_id`).

## 2. Shared Variables проекта

Settings → Shared Variables. Их наследуют все сервисы через `${{shared.NAME}}`.

```
TELEGRAM_TOKEN      = <токен от BotFather>
DATABASE_URL        = ${{Postgres.DATABASE_URL}}
REDIS_URL           = ${{Redis.REDIS_URL}}
ADMIN_IDS           = 123456789
BOSS_IDS            = 123456789,987654321
MANAGER_IDS         = 111111111
BASE_CURRENCY       = USD
TZ                  = Asia/Tashkent
TZ_OFFSET           = 5
BACKUP_TG_CHAT_ID   = -1001234567890
PHOTOS_TG_CHAT_ID   = -1009876543210
CHANNEL_ID          = -1005555555555
```

**`PHOTOS_TG_CHAT_ID`** (раньше `MACHINE_PHOTOS_TG_CHAT_ID`, старое имя
продолжает работать) — приватный канал, куда WebApp кладёт
фотографии техники (бот в нём администратор; можно тот же канал, что и для
backup). Своего файлового хранилища у проекта нет и не нужно: Telegram хранит
снимки бесплатно и вечно, а файловая система Railway эфемерна. Без переменной
загрузка из WebApp выключается и кнопка не рисуется — фото по-прежнему можно
прислать боту, то есть это деградация функции, а не поломка раздела. Туда же
кладутся фотографии товаров для витрины в канале.

**`CHANNEL_ID`** — ПУБЛИЧНЫЙ канал компании, в который уходят посты (витрина,
поступления, залежавшееся). Бот должен быть в нём администратором с правом
публикации. Без переменной кнопка «Опубликовать» отвечает понятным отказом, а
черновики собираются как обычно.

**`TZ_OFFSET` — не косметика.** Время в БД пишется в локальном кадре, и от него
считаются все пороги: просрочка долга, «зависшая» заявка, архивация проданной
техники, окно дельты остатков. Разъедется с реальным часовым поясом — счётчики
начнут врать молча, без единой ошибки в логах.

`ALLOWED_USERS` и `LEGACY_OPEN_BOT` **не задавайте**: новые пользователи должны
получать роль `guest` (нулевые права), а админ повышает их через `/addrole`.
Открытый режим был закрыт по итогам security-аудита (SECURITY.md, C1).

## 3. Миграция — строго до первого старта сервисов

`init_db()` умеет только `CREATE TABLE IF NOT EXISTS`. Всё остальное — `ALTER`,
backfill'ы, сидинг настроек — живёт в отдельной команде:

```bash
python -m tasks.migrate
```

Варианты запуска:

- **Pre-deploy Command** на сервисе `Webapp` (Settings → Deploy) — прогоняется
  перед каждым выкатом, идемпотентна;
- либо одноразовый сервис с этой командой, удалить после первого прогона.

Пока миграция не прошла — сервисы поднимать нельзя: они стартуют, но денежные
запросы упрутся в отсутствующие колонки.

---

## 4. Сервис `moysklad_bot`

- **Start Command:** `python bot.py`
- **Переменная сервиса:** `BOT_MODE=bot`

Что делает: long-polling Telegram и обработку команд. Фоновых циклов у него
больше нет — синхронизировать не с чем, учёт локальный.

---

## 5. Сервис `Webapp`

- **Start Command:** `python bot.py`
- **Переменные сервиса:** `BOT_MODE=webapp`
- **Settings → Networking → Generate Domain**
- **Settings → Healthcheck Path:** `/healthz`

Порт слушается из `PORT`, который Railway подставляет сам.

После получения домена:

1. добавить в Shared Variables `WEBAPP_URL = https://<домен>` (с `https://`, без
   слэша в конце — Telegram молча игнорирует WebApp-кнопку с не-HTTPS URL);
2. у @BotFather: `/mybots` → бот → Bot Settings → Menu Button → тот же URL.

## 6. Cron-задачи

Каждая — отдельный сервис Railway из того же репозитория, тип **Cron**, со своей
Start Command. Расписания в UTC.

| Сервис | Команда | Cron | Зачем |
|---|---|---|---|
| `cron-debts` | `python -m tasks.run_debts_notify` | `0 6 * * *` | утреннее напоминание по долгам |
| `cron-ops` | `python -m tasks.run_ops_monitor` | `30 6 * * *` | дневной пинг «N событий — откройте WebApp» |
| `cron-maintenance` | `python -m tasks.run_maintenance` | `0 3 * * *` | чистка дедупа, аудита, протухших ключей |
| `cron-backup` | `python -m tasks.run_backup` | `20 3 * * *` | дамп БД → gzip → приватный канал |
| `cron-machines-archive` | `python -m tasks.run_machines_archive` | `40 3 * * *` | проданная техника старше 90 дней → архив |
| `cron-money-report` | `python -m tasks.run_money_report` | `0 6 * * 1` | «Где деньги» руководству: дебиторка, прогноз, дисциплина |

Ночные разнесены по 20 минут намеренно: `run_backup` держит соединение под
дамп, а `run_maintenance` в это же время удаляет строки — пересекать их не надо.

`cron-money-report` шлёт отчёт **Rich Message** (Bot API 10.1): заголовки,
списки и таблицы прямо в чате. Если метод почему-то не пройдёт, задача сама
отправит тот же отчёт простым текстом — это штатное поведение, а не ошибка.
Пустой отчёт (нет ни долгов, ни ожидавшихся платежей) не отправляется вовсе.

`cron-backup` дополнительно требует `BACKUP_TG_CHAT_ID` и бота-администратора в
канале. Если `pg_dump` в образе окажется старее managed-Postgres, задача сама
переключится на version-independent дамп через libpq — это штатное поведение,
не ошибка.

**`Bad Request: chat not found` в логе `cron-backup`** значит ровно одно: дамп
собрался, но отправить его некуда. Бота нет в канале (или его оттуда удалили),
либо id записан без префикса `-100`. Проверка: переслать сообщение из канала в
@userinfobot и сверить id с переменной. Переменные cron-сервиса Railway НЕ
наследует автоматически — задавайте `BACKUP_TG_CHAT_ID` и на нём тоже.
В том же логе задача печатает состав дампа («N таблиц, M строк, крупнейшие: …»):
по нему видно, что бэкап не пустой, — размер файла на этот вопрос не отвечает.

## 7. Проверка после выката

1. **Логи `moysklad_bot`:** `Старт в режиме BOT_MODE=bot`, строка
   `Версия: version=<sha> branch=… commit='…'` и `Бот запущен в режиме: polling`.
2. **Health:** `curl https://<домен>/healthz` → `200` и `version` с тем же SHA,
   что в логах бота. Разошлись — один из двух сервисов не передеплоился
   (они выкатываются отдельно); то же самое покажет `/version` в боте одной
   строкой, без панели Railway.
3. **Бот:** `/start` → приветствие с кнопкой «Открыть», WebApp открывается и
   показывает главную (не «Доступ не выдан» — значит роль подхватилась из
   `ADMIN_IDS`).
4. **Склад:** «Склад → Каталог» показывает товары и остатки; «Накладные» —
   список расходных и приходных документов.
5. **Cron:** у каждого нажать Run и убедиться в коде выхода 0.
6. **Роли:** `/users` в боте показывает вас админом.

## Грабли, на которые легко наступить

### Polling и webhook несовместимы в двухсервисной топологии

`BOT_MODE=bot` **не умеет** webhook: приём апдейтов требует FastAPI в том же
процессе. При `TG_USE_WEBHOOK=1` он честно предупредит в логах и уйдёт в
polling, а перед polling выполнит `delete_webhook` — то есть **снесёт вебхук,
который только что установил сервис `Webapp`**. Получится флаппинг: кто
стартовал последним, тот и выиграл.

Выбирайте одно:

- **два сервиса → только polling** (`TG_USE_WEBHOOK` не задавать нигде) —
  штатная конфигурация;
- **webhook → один сервис `BOT_MODE=all`** с `TG_USE_WEBHOOK=1`,
  `TG_WEBHOOK_SECRET` и `WEBAPP_URL`.

### Склад нужно засеять ДО первого заказа

`python -m tasks.migrate` заводит склад по умолчанию (`seed_warehouses`). Без
строки в `warehouses` любая накладная отвергается «склад не найден», то есть
одобренная заявка не спишет остаток. Перенос каталога и контрагентов из
МойСклад — отдельным прогоном:

```
python -m scripts.migrate_from_moysklad --dry-run   # отчёт, ничего не пишет
python -m scripts.migrate_from_moysklad --apply     # перенос + сверка
```

Ненулевой код выхода означает РАСХОЖДЕНИЕ и обязан блокировать переключение:
обратной синхронизации после перехода нет, и разошедшийся остаток чинить
нечем. После `--apply` прогоните `python -m tasks.migrate` ещё раз — он
переведёт старые ссылки (заказы, лимиты, цены, фото) на наши id.

### Печать: контейнер должен ДОСТАТЬ до CUPS хоста

В образе стоит только клиент (`cups-client`), демон `cupsd` живёт на хосте.
Переменная `CUPS_SERVER` говорит клиенту, куда идти; пустая — печать
выключена, и кнопка «Распечатать» под документами не рисуется вовсе.

По TCP через docker-мост (`CUPS_SERVER=host.docker.internal:631`) на хосте
нужно разрешить его в `/etc/cups/cupsd.conf`:

```
Listen 172.17.0.1:631
<Location />
  Order allow,deny
  Allow from 172.16.0.0/12
</Location>
```

затем `systemctl restart cups`. Проверка изнутри контейнера:

```
docker compose exec bot lpstat -p
```

Пусто или «Unable to connect» — до CUPS не достучались; сеть до самого
принтера (Tailscale) тут ни при чём, это локальная настройка демона.

Альтернатива без открытия TCP — пробросить сокет
`/run/cups/cups.sock:/run/cups/cups.sock` и оставить `CUPS_SERVER` пустым;
сокет обычно `root:lp` 0660, а контейнер работает под `app`, поэтому доступ
проверьте тем же `lpstat -p`.

### Файловая система эфемерна

Ничего не пишите на диск контейнера. И **не поднимайте локальный Bot API
server**: `file_id` привязан к паре «бот + сервер», переезд обнулит все
`tg_file_id` в карточках техники. Решение «остаёмся на облачном Bot API»
зафиксировано в CLAUDE.md, пока таблица фотографий пустая.

### Смена `WEBAPP_URL`

После смены домена обновите URL и у @BotFather (Menu Button): Telegram хранит
его отдельно, и кнопка в композере продолжит вести на прежний адрес.

## Откат

Railway → сервис → Deployments → нужный деплой → **Redeploy**. Схема БД
обратно не откатывается: `tasks/migrate.py` только добавляет колонки и таблицы,
поэтому старый код с новой схемой работает. Обратное — новый код на старой
схеме — нет, поэтому миграцию гоняем первой.
