## 1. Лимиты запросов и поведение при 429

### Что у нас

`services/moysklad.py:101-104` — 3 попытки, база 0.5 с, ретраим `{429, 500, 502, 503, 504}`.
`services/moysklad.py:213-233` — цикл ретраев; на 429 читаем заголовок:

```python
retry_after = resp.headers.get("Retry-After")          # moysklad.py:218
delay = float(retry_after) if retry_after and retry_after.isdigit() \
        else _RETRY_BASE_DELAY * (2**attempt)          # moysklad.py:219-223
```

`services/moysklad.py:107-164` — брейкер: 5 подряд провалов → открыт на 60 с.

### Что говорит документация

`md/_general.md:205-212` — полный список rate-заголовков:

| Заголовок | Смысл |
|---|---|
| `X-RateLimit-Limit` | сколько запросов можно равномерно сделать за интервал |
| `X-Lognex-Retry-TimeInterval` | длина интервала, **мс** |
| `X-RateLimit-Remaining` | сколько осталось до 429 |
| `X-Lognex-Reset` | время до сброса ограничения, **мс** (0 = ограничения нет) |
| `X-Lognex-Retry-After` | время до сброса ограничения, **мс** |

**Заголовка `Retry-After` в документации нет.** Наш комментарий на
`moysklad.py:217` («МойСклад возвращает Retry-After для 429 — уважаем его»)
не подтверждается докой. Это ровно то, что описано в задаче как «сейчас мы ждём
фиксированный интервал»: ветка `float(retry_after)` практически мёртвая, всегда
срабатывает fallback `0.5 / 1.0 / 2.0` с.

Дополнительно (`md/_general.md:213-214`): заголовки **не отражают лимит на
параллельные запросы**; при его превышении отдаётся 429 с кодом ошибки **1073**
(`md/_errors.md:74`), а обычный rate-429 — код **1049** (`md/_errors.md:55`).
Это два разных класса 429, и лечатся они по-разному: 1049 — ждать, 1073 —
снизить конкурентность. Мы их не различаем.

`md/_restrictions.md:13-19` — ограничения, не зависящие от аутентификации:
- **не более 5 параллельных запросов от одного пользователя или решения**;
- не более 20 параллельных запросов от аккаунта;
- не более 20 МБ в запросе, не более 8 КБ в заголовках (включая URL);
- обязательный gzip (у нас есть — `moysklad.py:52`).

`md/_restrictions.md:29-40` — бюджет запросов за 3-секундное окно:
- токен решения: 45 запросов / 3 с;
- **токен пользователя: вес 2 с 12.05.2026 → 22 запроса / 3 с**; вес 3 с
  01.09.2026 → 15; вес 4 с 01.12.2026 → 11;
- `report/stock/all` и `report/stock/bystore` — 5 единиц за запрос независимо
  от способа аутентификации.

`md/_restrictions.md:52-57` — автоотключение доступа к API: >200 запросов/мин с
ошибкой 429 в течение последнего часа, либо >200 **идентичных** ошибочных
запросов/мин. Восстановление — только через поддержку МойСклад.

### Разрыв

1. **Читаем несуществующий заголовок.** Нужно `X-Lognex-Retry-After` (мс → делить
   на 1000), fallback — `X-Lognex-Reset`, и только потом экспоненциальный backoff.
2. **Не смотрим `X-RateLimit-Remaining` проактивно.** Он приходит на *успешных*
   ответах тоже — можно тормозить до 429, а не после.
3. **Конкурентность 8 > разрешённых 5.** `_POSITIONS_CONCURRENCY_LIMIT = 8`
   (`moysklad.py:570`) и `asyncio.Semaphore(8)` (`run_ms_reconcile.py:60`) —
   каждый сам по себе выше лимита, а работают они в разных процессах поверх
   одного аккаунта. `TCPConnector(limit=20)` (`moysklad.py:77`) равен лимиту
   аккаунта целиком. Часть наших 429 — это код 1073, и ретрай с backoff его не
   лечит, только снижение параллелизма.
4. **Бюджет втрое меньше ожидаемого.** Комментарий `moysklad.py:559-560` считает
   «~45 req/s»; фактически сегодня (токен пользователя) это ~7.3 req/s, а с
   1 декабря 2026 — ~3.7 req/s. При таком бюджете почасовой прогон реконсиляции
   на 1500 GET-ов занимает ~3.5 минуты сплошного насыщения лимита.
5. **Брейкер считает только подряд идущие ошибки.** Сценарий «каждый третий
   запрос — 429» его не откроет, но по правилу «>200 ответов 429/мин в течение
   часа» уводит аккаунт в автоотключение.

**Вывод:** менять — да. Приоритет: сначала конкурентность (MS-2, дешёвая правка
двух констант), потом заголовки (MS-1).

## 2. Массовое создание/обновление

### Что говорит документация

`md/_general.md:1155-1167`:
> При использовании метода POST вы можете указать в теле запроса вместо одной —
> массив сущностей. […] Лимит на создание, обновление и удаление объектов
> списком — **1000**. Если выполнение массового запроса занимает более 5 минут […]
> запрос завершится ошибкой по таймауту.

Массовое удаление — `POST /entity/{type}/delete`. Превышение 1000 элементов в
массиве → HTTP **413** (`md/_general.md:189`, `md/_restrictions.md:44-48`).
Для наших сущностей это документировано отдельно:
`md/documents/_customerOrder.md:1069` (Массовое создание и обновление Заказов
покупателей), `md/documents/_demand.md:1282` (то же для Отгрузок).

### Где мы ходим поштучно

**`tasks/run_ms_sync_retry.py:88-108`** — цикл `for p in pending:` →
`create_paymentin_for_payment(pid)`. Каждая итерация (`ms_payments.py:179-207`) —
это **GET pre-search по syncId + POST**. При `--limit 100` (дефолт) — до 200
запросов за прогон, каждые 15 минут. Сюда просится массовый POST:
один запрос вместо 100 POST-ов, плюс один списочный GET
`filter=syncId=a;syncId=b;…` вместо 100 pre-search-ей.
Осторожно: массовый ответ — массив, ошибку по отдельному элементу надо разбирать
поштучно и класть в `set_payment_ms_sync(..., status="failed")` только упавшим.

**`tasks/run_ms_reconcile.py:27-42, 63-116`** — здесь не создание, а чтение, но
поштучность та же и она дороже: `_doc_status` делает `GET entity/{entity}/{id}`
**на каждую строку выборки**. Верхняя граница за прогон — 500 (customerorder) +
500 (demand) + 500 (paymentin) = **1500 GET-ов в час** (лимиты из
`database.py:3938-3951`, env `MS_RECONCILE_LIMIT`, дефолт 500).

Схлопывается в списочный запрос через OR-семантику фильтра
(`md/_general.md:1241-1244`: «Если в поисковом запросе несколько раз встречается
условие типа "равенство" `=`, применённое к одному и тому же полю, то такое
условие интерпретируется как совокупность условий, разделённых логическим `ИЛИ`»)
и фильтрацию по ID (`md/_general.md:1333-1345`):

```
GET entity/customerorder?filter=id=<uuid1>;id=<uuid2>;…&limit=100
```
Пришедшие в `rows` — живы; наши id, которых в ответе нет, — удалены.

**Ограничение на размер батча:** не более 8 КБ в заголовках запроса, включая URL
(`md/_restrictions.md:16`), плюс HTTP 414 при превышении длины URL
(`md/_general.md:190`). Одна запись `id=<36 символов>;` = 40 байт → безопасный
батч ≈ **100-150 id** на запрос (и он же ровно равен `limit=100`). Итог:
1500 GET-ов → **15 списочных запросов**. Это ×100 к бюджету 429.

**Синк номенклатуры** (`snapshot.py:72-88`, `refresh_products/_categories/
_counterparties/_employees`) — поштучности нет, `limit=1000` + offset-loop, всё
корректно. Источник 429 здесь другой — см. п. 2.4 сводной таблицы и §5 ниже про
`report/stock/all`.

### Про остатки — отдельно (это второй источник 429)

`snapshot.py:234-247` тянет `report/stock/all` страницами по 1000. С февраля
2026 каждый такой запрос стоит **5 единиц лимита** (`md/notifications/rate-limits.md`).
При этом `_stock_debounce_loop` (`snapshot.py:295-317`) с `_DEBOUNCE_SEC = 2`
запускает полный pull через 2 секунды после каждого вебхука об изменении
остатков, а подписок, влияющих на остатки, у нас девять
(`ms_webhooks.py:31-41`). Активная отгрузка/приёмка в МС = полный re-pull каждые
~2 секунды по 5 единиц за страницу при бюджете ~7.3 единиц/с.

Документация даёт ровно то, что нужно (`md/reports/_report_stock.md:667-713`):
- `GET /report/stock/all/current?changedSince=<ts>` — только изменившаяся
  номенклатура, «все данные в одном ответе, без необходимости листания», и этот
  эндпоинт **не входит** в список подорожавших до 5 единиц;
- ограничения: `changedSince` не глубже 24 часов в прошлое; рекомендуется
  перекрытие интервалов; полный синк без `changedSince` — раз в сутки;
- отдаёт только `assortmentId` + количество, по одному `stockType` за запрос
  (нужно 2 запроса: `stock` и `reserve`), имена/группы/единицы у нас и так
  приходят из `refresh_products` (`snapshot.py:105`);
- `md/dictionaries/_webhookstock.md:1-20` — отдельный тип вебхука
  (`webhookstock`), который присылает готовый `reportUrl` уже с нужным
  `changedSince`, раз в 1-5 минут. Это заменяет и наши девять stock-подписок,
  и дебаунс-петлю.

## 3. Где expand схлопывает N+1

Правила (`md/_general.md:1487-1491`): `expand` работает только при `limit ≤ 100`
(иначе **молча игнорируется**), максимальная глубина вложенности — 3, применим и
к результатам создания/обновления.

### 3.1 Аналитика: позиции отгрузок — 15 запросов на открытие

Сейчас:
- `moysklad.py:525-534` (`get_shipments`) — список demand с `expand=agent,owner`;
- затем `moysklad.py:643-655` — `asyncio.gather` из 15 × `get_shipment_positions`;
- `get_shipment_positions` (`moysklad.py:582-616`) — свой offset-цикл с
  `expand=assortment,uom`.

То же в `get_employee_stats` (`moysklad.py:829-838`, 10 отгрузок) и
`get_counterparty_purchases` (`moysklad.py:725-729`, до 20 отгрузок).

Документация позволяет:
```
GET entity/demand?filter=…&expand=agent,owner,positions.assortment&limit=100
```
`positions.assortment` — глубина 2 из разрешённых 3, `limit=100` у нас уже стоит
(`moysklad.py:522`, `773`, `698`). Позиции приезжают внутри списка — отдельные
запросы не нужны вовсе.

**Оговорка, которую нельзя пропустить:** вложенный `positions` — это MetaArray
со своими `meta.size/limit/offset`. В примерах документации у одиночного
документа вложенный лимит 1000 (`md/documents/_customerOrder.md:300-304`), а в
списочном ответе встречается 100 (`md/documents/_customerOrder.md:1055-1059`).
Значит `get_shipment_positions` не выкидываем: сравниваем
`positions.meta.size` с `len(positions.rows)` и, если хвост обрезан, дотягиваем
пагинацией — ровно тот случай, ради которого пагинация и вводилась (CLAUDE.md
про >100 line items в B2B-заказе).

Второй нюанс: сейчас у позиций TTL-кэш на час (`moysklad.py:582`), а у списка —
60 с (`moysklad.py:501`). После схлопывания позиции будут перечитываться вместе
со списком раз в минуту. Запросов всё равно меньше (1 против 16), но трафик на
запрос вырастет — это осознанный размен.

### 3.2 Сотрудники: полный список на каждого менеджера

`ms_sync.py:121-136` — `sync_manager` вызывает `get_ms_employees()`, который
крутит до 20 страниц (`ms_sync.py:30-54`). `sync_all_managers`
(`ms_sync.py:198-216`) вызывает `sync_manager` **в цикле по всем пользователям**.
При 30 менеджерах и 150 сотрудниках в МС — 30 × 2 = 60 запросов там, где хватает
2. Здесь нужен не `expand`, а либо вынос списка за цикл, либо контекстный поиск
`?search=<имя>` / `?filter=name~<имя>` (`md/_general.md:1414+`, `md/_general.md:1452-1460`).
Матчинг у нас всё равно по подстроке имени (`ms_sync.py:148-159`) — оператор `~`
делает ровно это на стороне МС.

### 3.3 Что уже правильно

## 4. Фильтрация по `updated` — можно ли перенести окно T2.13 на сторону МС

### Что у нас

`services/database.py:3938-3951` — `_reconcile_window()`: порог
`now - MS_RECONCILE_WINDOW_DAYS` (дефолт 30) + `MS_RECONCILE_LIMIT` (дефолт 500).
Применяется в `get_orders_with_ms_customerorder` (`database.py:4041-4066`),
`get_orders_with_ms_demand` (`4071-4095`), `get_payments_with_ms_paymentin`
(`3954-3976`) — фильтр по **нашему** `updated_at`, чтобы не гонять по всей
истории заказов.

### Что позволяет API

`updated` — полноценное фильтруемое поле у всех трёх наших документов, с
операторами `= != < > <= >=`:
- `md/documents/_customerOrder.md:47`
- `md/documents/_demand.md:46`
- `md/documents/_payment_in.md:41`

Более того, есть поле **`deleted`** («Момент последнего удаления»), тоже
фильтруемое (`md/documents/_customerOrder.md:16`, `md/documents/_demand.md:19`,
`md/documents/_payment_in.md:17`), и параметр `isDeleted=true/false` для выборки
документов из Корзины (`md/_general.md:1274-1279`).

Формат даты для фильтра — `ГГГГ-ММ-ДД ЧЧ:мм:сс[.ммм]`, часовой пояс **MSK**
(`md/_general.md:1191-1200`, `md/audit/_audit.md:485-487`). Это важно: у нас
`updated_at` пишется в локальной TZ бота, и наивный перенос порога без
конверсии в MSK даст тихий сдвиг окна — та же категория бага, о которой
предупреждает CLAUDE.md про сравнение local-TZ строк с `NOW()`.

### Ответ: «в лоб» — нет, и вот почему

Задача реконсиляции — найти документы, которых в МС **больше нет**. Запрос
`entity/customerorder?filter=updated>=<cutoff>` возвращает существующие
документы. Удалённый документ не появится в такой выборке — но точно так же в
ней не появится и документ, который просто давно не менялся. Отличить «удалён»
от «не трогали» по этой выборке невозможно, если только не выкачивать **все**
живые документы и не вычитать множества — а это дороже, чем то, что мы делаем
сейчас.

Что реально работает вместо этого:

1. **`filter=id=…;id=…` (MS-4).** Вместо N GET-ов — один списочный запрос на
   батч наших id. Отсутствие id в ответе = документ удалён. Локальное окно
   `updated_at` при этом можно оставить как есть (оно ограничивает размер
   батча), а можно и расширить: 1500 документов — это 15 запросов вместо 1500,
   так что окно в 30 дней перестаёт быть вынужденной мерой и `MS_RECONCILE_LIMIT`
   можно поднять, не рискуя 429.
2. **`filter=isDeleted=true;deleted>=<cutoff>` — частичное решение.** Ловит
   документы, ушедшие в Корзину, одним запросом на тип. Не ловит жёсткое
   удаление (мимо Корзины) и зависит от того, включена ли Корзина в настройках
   аккаунта (`md/_general.md:1434-1437`). Как единственный механизм не годится,
   как быстрая предварительная проверка — годится.
3. **Аудит (MS-9, §7).** Даёт события удаления напрямую и с фильтром по времени.
   Это и есть настоящий «перенос окна на сторону МС».

**Вывод:** окно T2.13 остаётся локальным, но перестаёт быть узким местом после
MS-4; полностью снимает вопрос MS-9.

## 5. Шаблоны документов (demand на основе customerorder)

### Что у нас

`ms_demand.create_demand_from_request` (`ms_demand.py:230-316`) собирает demand
вручную: цикл по `items` → `positions` с `quantity/price/discount/vat/assortment`
(`ms_demand.py:231-258`), затем payload с `organization/agent/store/moment/
description/applicable` (`ms_demand.py:298-311`) и связь с заказом через

(`ms_demand.py:315-316`). Вызов — `order_workflow.py:649`, сразу после
`create_customerorder_from_request` (`order_workflow.py:612`).

### Что позволяет API

Шаблонный вызов есть (`md/documents/_common_info.md:3-30`):

> `https://api.moysklad.ru/api/remap/1.2/entity/<ключевое слово>/new` — в тело
> **PUT** передаётся meta документа-основания. […] В результате PUT запроса
> **НЕ будет создано нового документа** — возвращается «болванка» с
> предзаполненными полями, которую затем можно передать в запрос на создание.

Таблица оснований (`md/documents/_common_info.md:26`) прямо содержит
**Отгрузка (demand) ← Заказ покупателя (customerorder)**. Пример запроса и
ответа — `md/documents/_demand.md:1926-2060`: в ответе приезжают `owner`,
`group`, `moment`, `rate.currency`, `store`, `vatEnabled`/`vatIncluded`,
`positions` (с `quantity`/`price`/`assortment`) и уже проставленный
`customerOrder.meta` (`md/documents/_demand.md:2050-2058`).

### Стоит ли менять — скорее нет (P3)

Аргументы против:
- Шаблон подставит позиции и цены **из документа МС**, а у нас источник истины —
  локальная БД в копейках (`ms_demand.py:243`, комментарий про дрейф на x.xx5).
  Брать цены из шаблона — значит менять источник истины; брать шаблон и
  перезаписывать позиции — значит платить лишний PUT почти ни за что.
- Это +1 запрос на каждый апрув (PUT /new, затем POST).
- Оговорка из доки: при авторизации **по токену решения** в шаблоне не будет
  `owner`, `group`, `store`, `organization` (`md/documents/_common_info.md:13`) —
  то есть поведение зависит от типа токена, а мы их и так проставляем сами.

Аргументы за (почему стоит держать в голове):
- `vatEnabled`/`vatIncluded`/`rate` мы сейчас не передаём вовсе — МС подставляет
  дефолты аккаунта. Если когда-нибудь появится НДС или мультивалютность в МС,
  шаблон снимет этот класс расхождений разом.
- Связь «Заказ → Отгрузка» шаблон делает сам, без ручного `customerOrder.meta`.

**Итог:** документируем как известную альтернативу, в работу сейчас не берём.

## 6. syncId — сверка с документацией

### Документация

`md/_general.md:1142-1148`:
> Сущностям, у которых среди атрибутов присутствует поле **syncId**, оно
> необходимо для того, чтобы в случае сбоя при повторной отправке запроса на
> создание новой сущности не происходило дублирование объектов. Если в теле
> запроса на создание сущности указать сгенерированный на клиенте syncId, то
> **при повторной отправке этого же запроса (с тем же syncId) вместо создания
> сущности с идентичными полями в ответ придёт ранее созданная сущность**.
> Сущности, поддерживающие поле syncId, можно удалить, используя url типа
> `/entity/{type}/syncid/{id}`.

Тип поля — UUID, операторы фильтрации `=` и `!=`, «После заполнения недоступен
для изменения» (`md/documents/_payment_in.md:40`, `_customerOrder.md:45`,
`_demand.md:45`, `_sales_return.md:38`).

### 6.1 Правильно ли формируем — да

`ms_payments.py:159-161`:
```python
sync_id = str(_uuid.uuid5(_uuid.NAMESPACE_URL, f"bot-paymentin-{payment_id}"))
```
`moysklad.py:167-179` — та же схема, обобщённая: `uuid5(NAMESPACE_URL, f"bot-{entity}-{order_id}")`.

Соответствует требованиям: валидный UUID, детерминированный, содержит тип
сущности в seed → customerorder и demand одного заказа получают разные syncId
(критично, поскольку по доке syncId уникален в рамках аккаунта, а не типа).
Замечаний нет.

Мелочь на будущее: `ms_payments.py` формирует syncId локальным inline-кодом,
хотя в `moysklad.py:167` уже есть общий `order_sync_id(entity, id)`. Два
источника одной схемы — риск разъезда при правке. Чисто гигиеническое.

### 6.2 Pre-search перед POST — по доке избыточен

`moysklad.py:182-195` (`find_by_sync_id`) и `ms_payments.py:179-193` делают
`GET entity/{type}?filter=syncId=<uuid>&limit=1` **перед каждым** POST:
- `ms_customerorder.py:286-303` — для customerorder;
- `ms_demand.py:279-293` — для demand;
- `ms_payments.py:179-193` — для paymentin.

По документации повторный POST с тем же syncId сам вернёт существующий документ,
то есть дублей не будет и без pre-search. Это −1 запрос на каждый создаваемый
документ (на апруве заказа — минус 2: customerorder + demand).

**Но:** формулировка доки («вместо создания сущности **с идентичными полями**»)
допускает толкование, что при изменившихся полях поведение другое (обновление
вместо возврата). Прежде чем убирать защиту, которая закрывает двойное списание
остатков (`ms_demand.py:274-276`), это надо проверить боевым скриптом — по
образцу `tasks/verify_ms_returns`. Пока проверки нет, pre-search оставляем:
1 лишний GET дешевле дубля demand.

### 6.3 salesreturn без syncId — незакрытая часть T2.4

`ms_returns.create_salesreturn` (`ms_returns.py:81-90`) формирует payload
**без** `syncId`, хотя `md/documents/_sales_return.md:38` это поле поддерживает.
Вместо МС-стороннёй идемпотентности у нас компенсирующая логика: POST → если
`set_return_ms_id` проиграл гонку, **удаляем только что созданный документ** в МС
(`ms_returns.py:106-130`, WP-14). Это работает, но:
- дубль реально создаётся в МС (двигает склад и баланс контрагента) и живёт до
  успешного DELETE;
- DELETE — best-effort, при его провале остаётся orphan-документ;
- при краше процесса между POST и записью `moysklad_return_id` повторный вызов
  создаст второй возврат, и никакая гонка это не поймает.

С `syncId = order_sync_id("salesreturn", return_id)` МС просто вернёт ранее
созданный документ. Это прямо то, чего требует T2.4 («то же для customerorder и
demand») — для возвратов пункт остался невыполненным.

Побочно: `ms_cancel.reverse_customerorder` (`ms_cancel.py:56`) удаляет по id —
корректно; для документов с syncId доступен и `DELETE /entity/customerorder/syncid/{syncId}`,
что позволило бы отменять заказ, не храня `ms_customerorder_id`. Практической
нужды нет, ссылка у нас и так есть.

## 7. Аудит МойСклад — может ли заменить часть реконсиляции

### Что есть в API

`md/audit/_audit.md:1-22` — сервис накапливает события по всем сущностям.
Две модели: **контексты** (`GET /audit`) и **события** (`GET /audit/{id}/events`,
`GET /entity/{type}/{id}/audit`).

Типы событий (`md/audit/_audit.md:227-238`) включают: создание, обновление,
**удаление сущности или документа**, помещение в корзину, восстановление из
корзины, помещение/восстановление из архива.

Фильтры контекстов (`md/audit/_audit.md:473-527`):

| Фильтр | Значение |
|---|---|
| `entityType` | `customerorder`, `demand`, `paymentin`, … |
| `eventType` | `create`, `update`, **`delete`**, `puttorecyclebin`, `restorefromrecyclebin`, `bulkoperation`, … |
| `moment` | дата+время, операторы `>=` и `<=`, TZ = **MSK** |
| `employee` | href сотрудника — автора изменений |
| `source` | `remap-1.2`, `app`, `import`, `clearrecyclebin`, … |
| `uid` / `application` | uid или href решения (`md/_general.md:3692-3710`) |

В событии есть `entity` — meta самой сущности (`md/audit/_audit.md:247`), то
есть id удалённого документа мы получаем прямо оттуда.

### Что это даёт нам

Сейчас (`run_ms_reconcile.py:118-140`) прогон — до 1500 точечных GET-ов в час,
99.9% которых возвращают «документ на месте». Заменяется на:

```
GET /audit?filter=entityType=customerorder;eventType=delete;moment>=<последний прогон>
GET /audit?filter=entityType=demand;eventType=delete;moment>=<…>
GET /audit?filter=entityType=paymentin;eventType=delete;moment>=<…>
```

плюс `GET /audit/{ctx_id}/events` на каждый найденный контекст (обычно ноль).
**3-4 запроса вместо 1500.** По ним берём `entity.meta.href` → id →
`find_order_by_ms_customerorder_id` / `find_payment_by_ms_paymentin_id`
(`database.py:4014`, `database.py:3978`) → тот же
`apply_ms_customerorder_delete` / `apply_ms_demand_delete`
(`ms_sync_handler.py:325`, `483`). Логика применения не меняется вообще —
меняется только способ обнаружения.

Дополнительный бонус: `eventType=puttorecyclebin` ловит перемещение в Корзину
(наш `ms_cancel` именно так и удаляет — `ms_cancel.py:19`), а `eventType=update`
+ `source` может со временем заменить и вебхук `customerorder.UPDATE`.

### Оговорки, которые надо проверить перед внедрением

1. **Права.** Дока: «Изменения по конкретной сущности доступны пользователям при
   наличии прав на просмотр» (`md/audit/_audit.md:4`). Нужен токен с доступом к
   аудиту — проверить боевым read-only скриптом.
2. **Глубина хранения аудита** в документации не указана. При окне прогона в час
   это некритично, но пропущенные прогоны (простой сервиса > retention) создадут
   дыру → полный `filter=id=…`-проход (MS-4) остаётся как страховка, скажем,
   раз в сутки.
3. **`moment` в MSK** (`md/audit/_audit.md:485-487`) — тот же TZ-капкан, что и в §4.
4. **Пагинация** — стандартная, `limit`/`offset`, дефолт `limit=25`, **максимум 100**
   (`md/audit/_audit.md:96`); крутить offset-loop по конвенции CLAUDE.md.
5. Аудит **не заменяет** реконсиляцию полностью: он показывает события, а не
   текущее состояние. Расхождение, возникшее не через удаление (например, ручное
   изменение суммы), ловится нашим `_check_order_drift`
   (`ms_sync_handler.py:423-470`) по вебхуку UPDATE — это остаётся как есть.

**Вывод:** да, аудит заменяет самую дорогую часть реконсиляции. Рекомендуемая
конфигурация: аудит ежечасно (3-4 запроса) + полный `filter=id`-проход раз в
сутки как страховка (15 запросов) вместо нынешних 1500 запросов в час.
